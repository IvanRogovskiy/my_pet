# Постановка, доказательства и ревью

Редакция: 2026-10-14. Читать при выдаче задания и проверке сдачи. Это рабочие шаблоны для существующих практик, а не дополнительные задания. Заполнять только относящиеся к текущей части поля; короткий ответ в чате не требует комплекта файлов.

## Карточка задания

```markdown
# <ID задания> — <название>, версия <v1>, дата <дата>
Тема/часть: <номер>. Теория, нужная для решения: <конкретные части>.
Результат: <файл и путь от корня проекта / ответ в чате / работающий сценарий>.
Исходник: <commit или отдельная копия>; зависимости: <lockfile>; данные: <fixture>.
Среда: <ОС/архитектура, версии, доступные службы>; подготовка: <команда>.
Первый шаг: <действие, доступное сейчас>.
Контракт: <версия; входы, единицы, ошибки, повторы, права>.

| ID | Обязательный результат | Проверка и ожидаемый результат | Что предъявить |
| --- | --- | --- | --- |
| C1 | <наблюдаемое поведение> | <команда/действие и результат> | <код/вывод/ссылка> |

Сдать: <точный перечень>. Не проверяем здесь: <границы среды и задания>.
Изменения задания: <версия, причина, добавленный объём; либо нет>.
```

Для одной части выбрать 2–4 критерия. Итог темы объединяет уже выданные критерии и не требует переписывать работу. Большую матрицу отказов распределять по частям. Новые условия не применять к старой сдаче задним числом; обязательное исправление опасного поведения объяснить и оформить новой версией задания.

Из чистой копии должны воспроизводиться установка и проверки командами README. Зафиксировать версии Python/ОС/БД, область typecheck, seed и миграции. Историческую сдачу проверять с её зависимостями и данными, без поздних модулей, локальных `.env`, кешей и runtime-файлов. Сбой импорта при подготовке не доказывает ожидаемую бизнес-ошибку.

## Пример критериев: повтор заказа, тема 08/3

Учебный контракт v1: `Idempotency-Key` — непрозрачная регистрозависимая строка; окружающие пробелы запрещены, а не молча удаляются. Область уникальности — покупатель и операция. Представление тела для сравнения заранее определено в контракте. При первой успешной операции сохраняются заказ, HTTP-статус и тело результата; такой же запрос возвращает тот же результат, другой payload с тем же ключом — 409. Остаток резервируется один раз.

| ID | Проверка | Доказательство для ревью | Статус до запуска |
| --- | --- | --- | --- |
| C1 | Два последовательных одинаковых POST: одинаковые ID/статус/тело, один заказ и одно резервирование в PostgreSQL | Команда HTTP, ответы без cookies, SQL-сверка | Не проверено |
| C2 | Тот же ключ и иное количество: 409, заказ и остаток неизменны | Ответ и состояние до/после | Не проверено |
| C3 | Два конкурентных POST с тем же ключом: один эффект, согласованный результат обоих | Воспроизводимый тест на реальной PostgreSQL | Не проверено |

Команды привязать к действительным маршрутам и тестам ученика до сдачи. Например, `python -m pytest tests/integration/test_order_replay.py -q` уместна только после создания и предъявления этого теста. Наличие команды в шаблоне не означает выполненную проверку.

## Отчёт проверки

Для каждого критерия сохранить: версию задания → версию решения → команду/действие → среду → фактический результат → безопасный артефакт → статус. Статусы: **подтверждено**, **обнаружена ошибка**, **не проверено**. Для последнего указать причину и условие проверки. Автор запуска: проверяющий / ученик / агент в симуляции. Уровень доказательства: чтение кода / unit / PostgreSQL / HTTP / браузер / Linux / hosted CI / облако. Это разные границы проверки, а не рейтинг качества.

HTTP 200 не доказывает работу CSS и формы; локальный bind mount не проверяет права образа на Linux; рендер Helm не доказывает маршрутизацию; локальный pipeline не заменяет hosted job. Для обязательного критерия нужен именно оговорённый уровень. Дополнительный production-сценарий не становится обязательным только потому, что его ещё не проверили.

До вывода о дефекте решения проверить сам тест: правильный URL/селектор, детерминированные данные и порядок, реальную точку отказа и независимость expected от реализации. Не «лечить» нестабильную проверку retries или `allow_failure`. При неизвестной причине сохранить гипотезу и следующий диагностический шаг.

## Заполненные карточки замечаний

Примеры ниже вымышленные, имена файлов и строки относятся только к примеру. Они не являются результатом текущего запуска.

| Поле | R1: дефект кода | R2: дефект проверки | R3: ограничение среды | R4: необязательный совет |
| --- | --- | --- | --- | --- |
| Место | `orders/service.py:42` | `tests/test_orders.py:28` | Шаг Linux-проверки прав | `orders/views.py:18` |
| Основание | C1: одна резервация | Метод измерения N+1 из задания | C4 требует UID веб-сервера на Linux | Критерий не нарушен |
| Ожидание / факт | Остаток 4 после двух POST / стал 3 | Одинаковые строки в заданном порядке / сравниваются два неупорядоченных списка | Реальная проверка чтения / Linux отсутствует | Можно выделить именованную функцию / длинное, но корректное выражение |
| Воспроизведение | Один товар, stock=5; два POST qty=1 с ключом `demo-1`; SQL до/после | Один fixture; SQL без ORDER BY в обоих вариантах | Доступен только macOS bind mount; Linux-команда не выполнялась | Чтение кода; нет воспроизводимого функционального отказа |
| Влияние и важность | Блокирует C1: повтор списывает товар | Блокирует достоверность измерения, не доказывает дефект API | C4 остаётся непроверенным, это не ошибка ученика | Не блокирует приёмку |
| Объяснение / направление | Проверка повтора выполняется после изменения остатка; найти границу транзакции и сохранённого результата | Порядок SQL не обещан; задать одинаковую сортировку по уникальному ключу до сравнения | Запустить тот же образ с фактическим UID на согласованной Linux-среде | Обсудить читаемость и цену дополнительной абстракции |

Сначала объяснить причину и предложить диагностическое действие, затем подсказку по запросу; полное решение выдавать по просьбе ученика. Обсуждать альтернативы и их ограничения, а не только требовать конкретный стиль автора ревью.

## Диагностика затруднения и подсказки

По словам ученика и его попытке определить ближайшее затруднение. Если данных недостаточно, задать один конкретный диагностический вопрос; если причина уже видна, сразу дать подходящий следующий шаг.

| Затруднение | Следующее действие | Что проверить в ответе |
| --- | --- | --- |
| Неясно условие | Разобрать один вход, ожидаемый выход и состояние после отказа; попросить назвать результат соседнего случая | Ученик различает возвращаемое значение, исключение и побочный эффект |
| Неверная модель механизма | Дать один контрпример или предложить расписание событий, не готовую реализацию | Объяснение причины изменилось; правильный термин сам по себе недостаточен |
| Механизм понятен, код падает | Связать наблюдаемый вход, место изменения состояния и фактический результат; предложить один диагностический запуск | Ученик локализовал причину и может проверить исправление тем же примером |

Помощь усиливать по ответу: сначала направление поиска, затем механизм, затем минимальный разобранный пример по просьбе. Уровень подсказки выбирать по потребности, не требовать ритуального прохождения всех ступеней. На «одну подсказку» давать одно действие; полное решение — по явной просьбе. Сохранять альтернативные корректные реализации. Не объявлять приложенный traceback собственным запуском.

Если ведение состояния разрешено, записать точный запрос, выданную помощь и следующую самостоятельную попытку. Ответ после подсказки не превращать в доказательство самостоятельного переноса. [Три сценария проверки подсказок](../assets/teaching-benchmark/README.md) предназначены для аудита преподавателя; это не результаты настоящего ученика.

## Исправления и итог

| Замечание | Неуспешная проверка / версия | Повтор / исправленная версия | Затронутая регрессия | Итог |
| --- | --- | --- | --- | --- |
| R1 | <ссылка, команда, фактическое падение> | <та же проверка, результат> | <обычный заказ, rollback, конфликт ключа> | Закрыто / открыто / не проверено / снято как ошибочное |

Для исправления публичных прав проверить также сохранение приватных режимов: доступ веб-сервера к CSS не должен открывать `.env`. Один последний зелёный запуск без связи с исходной ошибкой недостаточен. После повторной проверки назвать выполненные и непроверенные критерии, оставшиеся ID и один следующий шаг. Зачёт задания не равен завершению темы или курса.

Сохранять ID и основание прежнего замечания между сдачами. Например, исправление области ключа `(buyer,key)` закрывает замечание о чужом результате, но не замечание об отсутствии конфликта другого тела. Исправление прав admin не закрывает всю практику, если новый код открыл чужие заказы buyer: прежнее замечание закрывается по проверке, регрессия получает отдельный ID. Не удалять закрытые замечания из истории.

При возражении ученика вернуться к исходному критерию и доказательству. Если проверяющий потребовал максимум 100, отсутствующий в v1, признать ошибочность этого требования, снять замечание и пересмотреть итог приёмки. Статус «снято как ошибочное» означает исправление ревью; статус «закрыто» — устранение установленного дефекта работы. Не требовать изменения корректного кода для формального закрытия. Если в код всё же попало лишнее ограничение, оценить его текущий эффект отдельным замечанием по v1, сохранив историю снятого требования.

Взаимное ревью предлагать при наличии партнёра: дать ему исходное задание и чистую копию, попросить запустить проверки и обсудить одно ADR. Если партнёра нет, преподаватель выполняет тот же проход; команда не является предпосылкой курса. Саморевью обозначать явно. Отдельный слепой проход полезен для [аудита материалов](course-maintenance.md), но не обязателен для каждой сдачи.

Для калибровки проверяющего существует [корпус из 20 синтетических работ](../assets/review-benchmark/README.md). Он включает корректные альтернативные решения и различает ошибки кода, теста, среды и постановки. Автоматический score оценивает метки и структуру, показывает пропущенные дефекты, ложные замечания и ошибочные отклонения корректных работ. Правильность, доказательность и полезность объяснения оцениваются отдельно по [четырём шкалам](../assets/review-benchmark/ASSESSMENT.md), с указанием оценщика и привязкой к версии ответа. Знание ключа исключает заявление о слепом независимом результате.

Для проверки повторного ревью предусмотрены [три последовательных цикла](../assets/review-benchmark/CYCLES.md). Сохраняются каждое сообщение, версия сдачи, ответ преподавателя и состояние после хода. Исполняемые проверки авторских решений и совпадение структурированных статусов не заменяют оценку объяснений и реакции на возражение.
