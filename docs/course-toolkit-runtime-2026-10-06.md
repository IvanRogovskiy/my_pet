# Реальный прогон лабораторий после освобождения места

Продолжение [первичной проверки комплекта](course-toolkit-2026-10-06.md). Дата: 2026-10-06. Задания и формат рабочих каталогов — `2026-10-06.1`; исправленный запускатель — `2026-10-06.2`.

Восемь лабораторий проверены на настоящих процессах Linux, контейнерах Docker и отдельном локальном kind. Для каждой завершён цикл **намеренный дефект → эталон → reset**, с кодами **1 → 0 → 1**. Исправлены пять проблем проверяющего и учебных примеров. Существующие 30 тем, 92 части и 6 факультативов сохранены; зачёты ученика не изменены.

Дополнительная проверка K27: после отдельно подтверждённого удаления SQL-маркера исправленная конфигурация больше не получает зачёт. Коды **до потери 0 → после потери 1 → после явного восстановления строки 0**. Автоматическая повторная выдача исходников не восстанавливает данные за ученика. Первую попытку инъекции не засчитали: она не установила потерю; перед повтором отдельный SELECT подтвердил нулевое число строк.

**38 тестов прошли на Linux/Python 3.11.2.** На macOS/Python 3.12.3: **37 прошли, 1 пропущен** с явной причиной — проверке прав нужен непривилегированный Linux UID. Этот тест отдельно выполнен в Linux-прогоне. Предыдущие проверки T24 настоящим Terraform, B29 на SQLite и C12 в модели DAG остаются результатами первичного отчёта; настоящий hosted GitLab здесь не запускался.

## Найденные и исправленные проблемы

1. **Повтор L02c ломал подготовку.** Marker становился `0400`, а следующий check пытался записать его снова и выдавал ошибку среды даже для эталона. Теперь fixture создаётся один раз; путь также проходит проверку symlink/hardlink. Добавлена регрессия bad → reference → reset под Linux UID.
2. **Проверка systemd могла принять неполное доказательство.** Команда `journalctl --user` не находила записи в общем журнале этого стенда, а неверный executable мог быть отклонён ещё клиентом `systemd-run`. Запуск через существующий `env` переносит намеренный отказ внутрь unit; `--user-unit` читает её записи, проверка требует журнал и сопоставляет active/MainPID/HTTP. Диагностика сохраняется до остановки.
3. **K27 проверял Service слишком рано.** В наблюдавшемся отказе исправленный Deployment уже завершил rollout, но SQL-маршрут ещё не был доступен. Добавлено ограниченное ожидание read-only проверок Service, отдельно от Ready. Постоянная ошибка остаётся ошибкой; регрессия проверяет и восстановление маршрута, и истечение ожидания.
4. **K27 скрывал потерю маркера.** Каждый запуск повторял INSERT и мог восстанавливать собственное доказательство сохранности. Инициализация теперь отмечается в данных лаборатории и не повторяется после reset. Проверены как отсутствие повторной инициализации, так и реальная потеря строки в PostgreSQL.
5. **Два asyncio-опыта влияли друг на друга на Python 3.11.2.** После TaskGroup в задаче оставалось состояние отмены, и следующий timeout завершался `CancelledError`. Опыты получили отдельные задачи-владельцы с обязательным await. Проверяются cleanup, отсутствие живых дочерних задач и неизменный счётчик отмены у вызывающей задачи; обе проверенные версии Python проходят.

Эти замечания внесены в запускатель, тесты, [инструкцию лабораторий](../backend-devops-theory/assets/labs/README.md), [урок asyncio](../backend-devops-theory/references/lessons/14-asyncio.md) и [журнал редакций скилла](../backend-devops-theory/references/course-maintenance.md). Поддержка старого формата рабочих каталогов сохранена.

## Среда и воспроизводимость

- Хост: macOS ARM, Python 3.12.3; Docker 24.0.5, Linux/aarch64.
- Отдельный kind 0.29.0, Kubernetes 1.33.1, Helm 3.18.3.
- Linux внутри собственного kind node: Debian 12, Python 3.11.2, systemd 252.39, пользователь `learner` с UID 1500.
- Для Linux-опытов в этом node подготовлены D-Bus/user manager, доступ к журналу и ansible-core 2.19.13; зависимости установлены только в отдельное окружение аудита.
- Python-образ содержит Python 3.12.14; PostgreSQL-образ — 16.15. Конкретные image IDs и digest-ссылки сохранены в manifest.

Образы уже были в локальном Docker. При загрузке в kind registry index digest не появился как доступная ссылка runtime: локальный импорт имел собственный manifest digest. Для обоих образов проверен фактический manifest в containerd и добавлена соответствующая digest-ссылка на тот же образ. Инструкция теперь предупреждает об этом различии; замена digest произвольным хешем не предлагается.

Обычный запускатель по-прежнему не устанавливает зависимости, не создаёт кластер и не запускает VM. Подготовка этой среды была отдельным авторским действием. Linux в kind подтверждает процессы, systemd, права и Ansible в данной среде; он не заменяет проверку загрузки полноценной VM, SSH, облачных прав или эксплуатации production.

Перед прогоном было около **19 ГиБ** свободного места, после — около **17 ГиБ**. Это наблюдаемый расход при уже скачанных образах, а не обещание такого же расхода на чистом компьютере.

## Доказательства и состояние стенда

[Manifest с версиями, SHA-256 исходников и доказательств](course-toolkit-runtime-2026-10-06/manifest.json) ссылается на 27 JSON-отчётов: три фазы восьми лабораторий и три проверки потери/восстановления маркера. Коды 1 в фазах broken/reset — ожидаемое обнаружение дефекта, не неудача авторского прогона. Рабочая папка и точный контекст сохранены в manifest; kubeconfig и реальные credentials в отчёт не включены.

Обе лабораторные deployments масштабированы в 0; transient user units и временные Docker-контейнеры завершены. Отдельный node остановлен после проверки; его данные и PVC сохранены для продолжения. Старый кластер и облачная VM не запускались. Никакой общий prune или удаление пользовательских volumes не выполнялись.

Хеши 671 Markdown/JSON-файла прежнего `learning/` и `course-audit/` остались прежними. Условные модели C12/B29, восстановление SQLite и локальный rollback по-прежнему имеют явно описанные границы; внешние системы и независимое слепое ревью не объявлены проверенными этим прогоном.
