# Запускаемые диагностические лаборатории

Версия заданий `2026-10-06.1`, редакция запускателя `2026-10-06.2`. Рабочие каталоги первой редакции совместимы; `runner_revision` в новых отчётах отличает исправленную проверку. Python 3.11+, macOS/Linux; Linux/systemd и кластерные случаи требуют своих сред. Используется стандартная библиотека Python, установки зависимостей и скачивания образов по умолчанию нет. Это изолированные упражнения существующих тем OrderFlow, не вводный проект.

Команды ниже — от корня репозитория. При установленном skill заменить путь на реальный путь к `assets/labs/lab.py`. Код запускается обычными локальными процессами с правами текущего пользователя; каталог лаборатории изолирует данные и имена ресурсов, но не является sandbox для недоверенного кода.

Автоматическая подготовка отдельного Linux/kind с собственными CLI описана в [BOOTSTRAP.md](BOOTSTRAP.md). Для настоящих конкурентных PostgreSQL-операций и RabbitMQ есть [четыре backend-лаборатории](../backend-labs/README.md). Эти наборы дополняют существующие 11 случаев, их результаты не смешиваются с локальными моделями.

## Обычное задание

```sh
python3 backend-devops-theory/assets/labs/lab.py list
python3 backend-devops-theory/assets/labs/lab.py prepare /tmp/of-b29-student --case B29
python3 backend-devops-theory/assets/labs/lab.py check /tmp/of-b29-student
```

`prepare` требует нового каталога и выдаёт намеренно неисправный вариант. Сначала прочитать `ASSIGNMENT.md`, затем изменять файлы `work/`, повторять `check` и объяснять причину. Для T24 изменяется только `work/plan.sh`; HCL — неизменный fixture проверяющего. Для L02a/L02b/L02c, D10 и K27 условие задаётся в `work/config.json`; C12 — `work/pipeline.json`, A25 — `work/playbook.json`, R26 — Dockerfile/приложение, H28 — chart, B29 — `work/replay.py`.

Каждый check сохраняет отдельный JSON в `evidence/`: ID задания, редакция, ОС/Python, SHA исходников, наблюдения и результат. Exit **0** означает выполнение только заявленного уровня проверки, **1** — нарушение, **2** — среда/подготовка не проверена. Другие exit codes внешнего инструмента остаются внутри отчёта; например, Terraform diff=2 не равен «среда недоступна» запускателя.

```sh
python3 backend-devops-theory/assets/labs/lab.py reset /tmp/of-b29-student
```

Reset возвращает выданные исходники к сломанному варианту. Сначала сохранить нужный diff: изменения этих файлов будут перезаписаны. `data/`, `evidence/` и дополнительные файлы ученика сохраняются. Reset не удаляет volumes/PVC, namespace, чужие процессы и образы. Ссылки наружу и уже существующий каталог не принимаются, одновременные CLI check/reset одного каталога запрещены.

## Среды и границы доказательства

| ID | Что реально выполняет check | Что подготовить |
| --- | --- | --- |
| L02a | Transient systemd user unit, journal/status/PID/HTTP; затем stop | Linux с работающим `systemctl --user`, Python текущего пользователя |
| L02b | Два собственных процесса на loopback; проверка PID ответа и остановка только своих процессов | Разрешение ОС/sandbox на bind 127.0.0.1 |
| L02c | Настоящее чтение через каталог под непривилегированным Linux UID | Linux, запуск не от root; после проверки доступ к каталогу восстановлен |
| D10 | Docker health + host HTTP до/после recreate, маркер на bind mount | Уже запущенный Docker, локальный Python image по digest |
| C12 | Детерминированная модель зависимостей с failed/successful gate | Только Python; **это не hosted GitLab** |
| T24 | Реальный local backend: apply синтетического terraform_data и plan для 0/2/1 | Terraform >=1.4,<2 в PATH или `--terraform`; provider/cloud не используются |
| A25 | Настоящий playbook и systemd unit; 4 прогона, changed/PID/хеш/HTTP, check-mode | Linux user manager, Ansible в PATH или `--ansible` |
| R26 | Два собранных образа, штатный CMD, SQLite expand, чтение/запись старым образом после rollback | Docker и локальный Python base по digest; **это не PostgreSQL или облачный релиз** |
| K27 | PostgreSQL Pod/PVC, локальная готовность, Service, SQL-маркер, rollout | Уже существующий локальный kind, default StorageClass, PG image уже загружен в nodes |
| H28 | Настоящий Helm --wait, EndpointSlice и HTTP через Service | Локальный kind, Helm, Python image в nodes |
| B29 | Реальные SQLite transactions/receipts/replay новой генерации | Только Python; **это не pg_restore, шифрование или offsite** |

Docker/кластерный preflight требует минимум 5 GiB свободного места хоста; Docker также проверяет запас внутри своей файловой системы. Это нижняя граница данных маленьких опытов, не вместимость полного курса. Предварительно оценить место образов/кластера. Runner не запускает Docker Desktop, не скачивает image и не создаёт kind/VM. При нехватке ресурса возвращается exit 2.

Для L02a/A25 недостаточно наличия файла `systemctl`: нужны работающий user manager, D-Bus, `XDG_RUNTIME_DIR` и доступ текущего пользователя к журналу своей службы. Проверяется `journalctl --user-unit=<имя>`: он подходит и для общего журнала без отдельного persistent user journal. Отсутствие записей означает непроверенную среду. Проверяющий сопоставляет `MainPID` с PID HTTP-ответа и требует `ActiveState=active`. Ошибка L02a запускается через существующий `env`, чтобы отказ произошёл внутри unit и оставил журнал, а не был отклонён клиентом `systemd-run` до создания службы.

`--image` принимает **локально имеющийся Python-образ** с `python` в PATH и стандартной библиотекой, в форме `repository@sha256:<64 hex>`. Для K27 используется `--postgres-image` с PostgreSQL 16 и обычными `postgres`, `pg_isready`, `psql`. Эти требования к выбранному образу фиксируются в паспорте; конкретная совместимая пара подтверждается реальным запуском, а не названием тега. `--context` обязателен для K27/H28: только `kind-*` с loopback API endpoint. Например, к команде check добавляются `--context kind-orderflow-labs --image <ваш-локальный-digest>`; placeholders не запускать буквально.

После `kind load docker-image` образ может присутствовать в node только под тегом. Проверить `crictl images --digests` внутри **выбранного учебного node**: при `imagePullPolicy: Never` точная передаваемая digest-ссылка должна быть доступна runtime. В проверенном импорте Docker → kind digest локального manifest отличается от registry index digest. Брать фактический manifest из `ctr --namespace k8s.io images ls`; при необходимости добавить ему ссылку `repository@<этот digest>` через `ctr images tag` в том же namespace. Не подставлять произвольный хеш и не считать digest разных объектов взаимозаменяемым. Редакция и конкретная проверенная пара записаны в отчёте runtime.

D10 публикует случайный свободный порт только на 127.0.0.1. R26 использует локальные уникальные теги лишь для двух собственных build-артефактов, записывает image IDs и удаляет их после проверки; это не контрольные теги этапов курса. Общий prune и публикация в registry не выполняются.

## Кластер: завершение и сохранённые данные

Runner создаёт namespace `oflab-<UUID>`, сохраняет UID и проверяет принадлежность при повторе. Диагностика собирается до остановки; все deployments этого отдельного namespace масштабируются в 0. PVC остаётся для проверки сохранности маркера. После работы проверить `evidence/cluster-last-diagnostics.json`, особенно результат stop: при недоступном API остановка могла не состояться.

В K27 первая успешная подготовка отмечается в `data/postgres-seeded.json`. Повторный check и reset не восстанавливают исчезнувшую строку автоматически: потеря маркера должна провалить проверку. После Ready отдельно ожидается SQL-маршрут через Service с конечным сроком; успешный rollout не заменяет этот запрос.

Для удаления лаборатории после завершения: взять **точные** context/namespace/UID из её записи, сверить текущий UID и label `course.owner` через kubectl, сохранить необходимые данные и лишь затем удалить этот конкретный namespace. Это явное удаление данных, не часть reset. Не использовать `--all` на уровне namespaces и не удалять весь кластер. Контекст другой машины или namespace с другим UID не принимается за прежний стенд.

## Авторская проверка

Команда `reference <каталог>` устанавливает эталон только в известные исходники `work/`. Она предназначена для проверки материалов после самостоятельной попытки, не выдаётся как первый шаг ученику. Цикл автора: prepare → check с ожидаемым дефектом → reference → check успешно → reset → дефект снова обнаружен. Если первый check дал 2, дефект ещё не воспроизведён. Эталон не является единственной допустимой реализацией: проверки должны принимать альтернативу с тем же поведением.

Для C12 можно скопировать `work/pipeline.json` как `.gitlab-ci.yml` в явно выбранную учебную ветку (JSON совместим с YAML), выполнить настоящий pipeline, затем отдельно сменить исход gate на успешный. Не переносить это в рабочий проект. Локальная модель принимает как явный needs на gate, так и правильную зависимость через stages; условные rules/extends требуют отдельного hosted-прохода и не получают локального зачёта.

```sh
python3 -m unittest discover -v -s backend-devops-theory/tests
```

Тесты проверяют lifecycle, сохранность данных, защиту границ и доступные локальные механизмы. Mock-проверка защиты Docker/kubectl не является реальным запуском инфраструктуры. Первичная матрица опубликована в `docs/course-toolkit-2026-10-06.md`, продолжение с реальными Linux/Docker/kind — в `docs/course-toolkit-runtime-2026-10-06.md` основного репозитория.
