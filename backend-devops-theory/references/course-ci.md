# Проверки репозитория курса

Этот режим нужен автору при изменении материалов; ученику не требуется запускать CI для обычного урока. Файлы `.github/workflows/course.yml` и `scripts/course_ci.py` находятся в основном репозитории, а не в установленной копии скилла.

## Быстрый набор

```sh
python3 scripts/course_ci.py fast
python3 scripts/course_ci.py evidence
```

`fast` запускает все найденные unit-тесты, кроме явно выделенных HTTP/TLS/Linux-проверок. В него входят ссылки и карта частей, оценщики, версии формата, контрпримеры, защита артефактов и макеты инфраструктурных вызовов. Новый test-модуль включается автоматически. Неожиданный пропуск теста и пустой выбор дают ненулевой код.

`evidence` проверяет каждый файл и точный состав двух замороженных отчётов — `teaching-reliability-2026-10-14` и `course-hardening-2026-10-17`, затем запускает их пересчёт. Исторические исходники из старых манифестов не сравниваются с изменяемым рабочим кодом. Отдельно текущий оценщик должен сохранить прежние результаты шести записей `.1` и восемнадцати `.2`; неудачный исторический формат остаётся неудачным. Пересчёт проверяет целостность внешних оценок, не переоценивает их смысл. При новом опыте добавить новый отчёт и его manifest в список EVIDENCE; старые результаты не переписывать ради зелёного CI.

Workflow выполняет эти команды на Ubuntu 24.04 и macOS 15, Python 3.11/3.12, при push/PR с изменениями курса, проверок или docs. Матрица в конфигурации — заявленные проверки будущего CI; фактически пройденные среды перечисляются в отчёте конкретного запуска. Выбор macOS 15 учитывает [объявленное прекращение macOS 14](https://github.com/actions/runner-images/issues/13518).

## Проверки с настоящими сервисами

```sh
python3 -m pip install -r backend-devops-theory/assets/network-lab/requirements.txt
python3 scripts/course_ci.py runtime
```

`runtime` требует непривилегированного Linux-пользователя и установленной cryptography: права файлов, loopback HTTP, отсутствие записи через GET, реальные TLS-исходы и остановка fixture. Недостающая зависимость не превращается в успешный пропуск.

В ручном `workflow_dispatch` отдельно включаются `runtime` и `backend`. Второй поднимает собственный закрытый PostgreSQL/RabbitMQ-стенд и выполняет B07/B08R/B08I/B17 с ожидаемыми кодами bad/reference/reset = 1/0/1. Setup → health → audit выполняются последовательно, поскольку используют общую блокировку стенда. Шаг `always()` останавливает только созданные этим job контейнеры; hosted runner затем утилизирует своё временное окружение. Локально stop сохраняет volumes и результаты согласно [жизненному циклу стенда](../assets/backend-labs/README.md).

Автоматического расписания, облачных ресурсов и секретов workflow не использует. Actions закреплены по SHA, `GITHUB_TOKEN` имеет только `contents: read`, credentials checkout не сохраняются. Синтаксис проверен по [официальному описанию workflow](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax); использованы опубликованные [checkout v6.0.2](https://github.com/actions/checkout/releases/tag/v6.0.2) и [setup-python v6.0.0](https://github.com/actions/setup-python/releases/tag/v6.0.0).

Пути стенда вычисляются оболочкой через `$RUNNER_TEMP` внутри шагов. Контекст `runner` недоступен в `jobs.<job_id>.env` согласно [таблице доступности контекстов](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#context-availability): первое опубликованное описание workflow было отклонено до запуска jobs из-за этой ошибки. Проверка обычным YAML-парсером её не выявляет; фактический статус workflow проверять в GitHub Actions.
