# Транзакция, последняя единица и повтор запроса

Редакция 2026-10-06. Углублённый материал к 08/1–3; предпосылки 04, 05–07. Не заменяет часть 08/4 об оптимизации. Выполняемый пример требует Python 3.11+; опыт изоляции — отдельной PostgreSQL. Это развитие существующего OrderFlow.

## Почему заказ может быть неверным при неотрицательном остатке

В OrderFlow осталась одна единица товара. Два покупателя одновременно видят её в каталоге. Требование относится к результату: успешен один заказ, одна резервация; второй получает согласованный отказ. Проверять только `stock >= 0` недостаточно: можно сохранить ноль, но подтвердить два заказа.

Рассмотрим конкретное чередование. Обработчик A прочитал 1. До его записи B тоже прочитал 1. Оба рассчитали новое значение как `прочитанное - 1`, затем по очереди записали 0. Ни отрицательного числа, ни исключения нет. Ошибка — решение о доступности принято по устаревшему чтению. Транзакция объединяет операции в единый commit/rollback, но корректность такого алгоритма зависит ещё и от изоляции и блокировок. Уровни изоляции имеют разные правила видимости; условия PostgreSQL нужно проверять именно на PostgreSQL. [Изоляция PostgreSQL 16](https://www.postgresql.org/docs/16/transaction-iso.html).

| Шаг | A | B | Остаток |
| --- | --- | --- | --- |
| 1 | Читает 1 | — | 1 |
| 2 | — | Читает 1 | 1 |
| 3 | Принимает заказ, пишет 0 | — | 0 |
| 4 | — | Принимает заказ, пишет ранее рассчитанный 0 | 0, но заказов два |

Исполняемая модель этого расписания:

```sh
python3 backend-devops-theory/assets/examples/mechanisms.py transactions
```

Ожидается `accepted=["A","B"]` при `remaining=0`. Вторая половина примера выполняет два условных UPDATE в SQLite и получает `[1,0]` изменённых строк. Это демонстрация различия алгоритмов, не конкурентный PostgreSQL-тест; вывод явно содержит `postgres_concurrency_verified=false`.

## Два способа принять решение под защитой БД

Первый вариант связывает проверку и изменение в одном SQL-операторе. Фрагмент предполагает уже созданную таблицу `stock(sku, qty)`:

```sql
UPDATE stock SET qty = qty - 1
WHERE sku = 'demo' AND qty >= 1
RETURNING qty;
```

Приложение обязано проверить результат. Изменена одна строка — резервация произошла; ни одной — нельзя подтверждать заказ как успешный. Запись заказа и резервация должны находиться в одной транзакции, иначе ошибка вставки заказа оставит товар зарезервированным без заказа.

Второй вариант нужен, когда решение зависит от нескольких полей: внутри транзакции заблокировать строку через `SELECT ... FOR UPDATE`, затем прочитать актуальное значение и изменить его. Для заказа с несколькими товарами определить единый порядок захвата строк, например по SKU. Если два обработчика берут одни строки в противоположном порядке, появляется возможность дедлока. PostgreSQL разрешает дедлок прерыванием одной из транзакций; приложение должно корректно обрабатывать такой исход. [Блокировки PostgreSQL](https://www.postgresql.org/docs/16/explicit-locking.html).

В Django граница `transaction.atomic()` охватывает всю локальную операцию. Она не откатывает произвольное изменение Python-объекта, отправленное письмо или запрос к внешнему провайдеру. После исключения нельзя продолжать работу, опираясь на изменённый в памяти остаток как на подтверждённое состояние. [Транзакции Django](https://docs.djangoproject.com/en/5.2/topics/db/transactions/).

## Повтор — другая задача

Даже при правильной защите последней единицы клиент может повторить уже успешный запрос после потери ответа. Для этого нужен отдельный контракт идемпотентности: область ключа, канонизация payload, сохранённый результат, конфликт при другом теле. Блокировка остатков не сообщает, выполнялась ли именно эта операция раньше.

Пример: покупатель 7 отправил ключ `K` с одной позицией. Повтор того же запроса должен вернуть его прежний заказ. Покупатель 8 может использовать `K` независимо. Если область уникальности — только строка ключа, сервер смешает две операции. Если тело не сравнивается, количество 2 с прежним ключом будет ошибочно принято за повтор количества 1. Эти правила определяются до кода в [контракте](../business-contract.md).

## Самостоятельная практика

В текущем проекте подготовить отдельный PostgreSQL fixture с одной единицей и два независимых соединения. Управлять началом попыток барьером/сигналами, не случайным `sleep`. Сдать тест, его вывод, конечные строки заказов/остатка и объяснение границы транзакции.

Критерии: (1) одна резервация и один успешный заказ при конкуренции; (2) ошибка записи заказа откатывает остаток; (3) повтор ключа не создаёт эффект, другой payload даёт объявленный конфликт; (4) другая учётная запись имеет независимую область ключей. Если PostgreSQL недоступна, модель расписания остаётся подготовкой, критерий конкуренции — непроверенным.

Перед подсказкой объясни: почему ноль на складе не доказывает корректность; что именно защищает выбранная блокировка; где заканчивается гарантия транзакции при HTTP-вызове; чем конфликт ключа отличается от нехватки товара. Направления подсказок: сначала нарисовать расписание, затем найти решение по старому чтению, затем сопоставить SQL-результат с созданием заказа. Следующий шаг — проверка своей реализации на заданном расписании.
