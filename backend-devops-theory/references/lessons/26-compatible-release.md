# Обновление приложения, которое можно откатить после миграции

Редакция 2026-10-06. Материал к 26/2–3, после CI, Terraform и Ansible. Не заменяет настройку доступа и promotion в 26/1. Учебный пример Python/SQLite показывает совместимость клиентов со схемой; лаборатория R26 отдельно запускает настоящие старый и новый Docker-образы.

## Откат образа не откатывает уже записанные данные

В OrderFlow добавляется комментарий к доставке. Новый API умеет его записывать, старый worker продолжает читать заказ. При rolling update некоторое время существуют обе версии. После неудачного выпуска мы хотим вернуть старый образ, но база уже изменилась и могла получить новые записи.

Поэтому «старый образ стартует» — лишь один пункт проверки. Он должен прочитать новую схему, записать допустимые данные и безопасно обработать сообщения, которые оставила новая версия. Откат БД отдельно может потерять уже принятые записи. Решение принимается для конкретного изменения, а не для слова rollback вообще.

Рабочая последовательность для добавления необязательного поля: расширить схему, выпустить совместимый код, заполнить старые строки повторяемым backfill, включить поведение по выбранному механизму. Удаление старых полей и запрет старого формата откладываются до завершения окна совместимости. У конкретного ALTER TABLE есть собственные блокировки и стоимость; добавление поля не означает автоматически обновление без задержек. [ALTER TABLE PostgreSQL](https://www.postgresql.org/docs/16/sql-altertable.html).

## Два старых клиента на одной новой схеме

```sh
python3 backend-devops-theory/assets/examples/mechanisms.py release
```

Сначала создаются `orders(id, amount)` и заказ на 250. Затем появляется nullable `note`. Старый клиент читает явные `id,amount` и вставляет только `amount`: эти действия продолжают работать. Новый клиент записывает note. После условного отката старый снова читает и пишет; ожидаемые суммы четырёх строк — 250, 100, 150, 200.

Другой старый клиент делает `SELECT *`, затем распаковывает строку ровно в две переменные. После расширения схема возвращает три значения, и такой клиент падает. Ошибка показывает, почему нельзя объявить любую добавочную колонку безопасной без проверки потребителей. В примере `select_star_tuple_broken=true` — специально обнаруженный контрпример, не успешный runtime-прогон Django.

Backfill обновляет только строки `WHERE note IS NULL`. Первый запуск меняет три строки, повтор — ноль. В реальном проекте ещё нужны границы партии, журнал прогресса и поведение при прерывании. Для Django изменение данных следует согласовывать с историческим состоянием моделей в миграции; текущая модель приложения не всегда соответствует моменту миграции. [Миграции Django](https://docs.djangoproject.com/en/5.2/topics/migrations/).

## Таблица до выпуска

| Сочетание | Проверяемое поведение |
| --- | --- |
| Старый API + расширенная схема | Старое чтение и запись |
| Новый API + старый worker | Сообщение совместимо или выпуск этого сочетания запрещён |
| Старый API после отката + новое сообщение в очереди | Предсказуемая обработка без повторного бизнес-эффекта |
| Новый API + завершённый backfill | Новое поведение и повтор backfill без изменений |

Необязательно поддерживать все сочетания: можно явно ограничить порядок обновления. Тогда pipeline должен не допустить запрещённого сочетания, а runbook объяснить восстановление после частичного выпуска.

Сборка образа не проверяет его CMD. Образ может успешно собраться и пройти тесты, выполненные отдельной командой, но упасть при штатном запуске. R26 создаёт два образа на одном закреплённом локальном Python base, выполняет expand, запускает новую версию и возвращается к старому образу. Проверяются отдельные image IDs, HTTP, старые строки и сохранение расширенной схемы. Данные лежат в собственном каталоге лаборатории. Это локальный Docker/SQLite опыт, не подтверждение PostgreSQL-миграции или облачного promotion.

## Самостоятельная практика

В текущем OrderFlow добавить согласованное поле заказа и записать таблицу допустимых сочетаний. Сдать миграцию, повторяемый backfill, результаты old/new/rollback и идентификаторы артефактов. По [инструкции лабораторий](../../assets/labs/README.md) можно сначала диагностировать R26; Docker требует достаточного места и локального образа по digest.

Критерии: (1) старый код читает и пишет после expand; (2) повтор backfill не меняет уже обработанное; (3) неисправный runtime блокирует продвижение; (4) реальный откат к прежнему образу сохраняет данные и работоспособность. Если изначальное задание требует worker/event-совместимость, приложить отдельный опыт с очередью: локальный пример не проверяет этот путь.

Самопроверка: какое изменение делает старый код несовместимым; зачем отделять expand от contract; почему повторная сборка для production ослабляет доказательство staging; какие данные могли появиться до rollback? Подсказки: начать с таблицы сочетаний, проверить явные столбцы и формат события, записать допустимое состояние после каждого шага. Следующий шаг — выполнить rollback после уже состоявшейся миграции.
