# GitLab: доступ, CI и доставка

Редакция: 2026-10-06. В теме 12 читать доступ и CI; Terraform добавляется только в 24, deploy в 26, кластерный gate — в 28. Шаблоны относятся к выбранному учебному проекту, не к произвольным рабочим репозиториям.

## Выбрать проект и проверить каналы

Записать URL проекта, ветку, видимость, место работы и границы изменения CI/защиты. Вход в собственный аккаунт не выбирает проект автоматически. Подходит существующий учебный репозиторий; отдельный приватный полезен для изоляции runner, переменных и экспериментов, но не обязателен. Не переносить учебные дефекты в рабочий проект.

| Канал | Фактическая проверка | Что она не доказывает |
| --- | --- | --- |
| API identity/project | Аутентифицированное чтение выбранного проекта | Git clone/push |
| Git | Чтение refs, clone; при разрешении — push учебной ветки | Доступ к registry или state |
| Runner | Малый реальный job на выбранном executor | Online не значит, что shell/Docker запускается |
| Registry | Push и чтение manifest учебного digest | Deploy этого образа |
| Branch protection | Правила + реальный запрет merge failing MR в учебной ветке | Одна зелёная локальная проверка не проверяет защиту |
| HTTP state, с темы 24 | Аутентифицированные read/write/lock в отдельном state | Git/API OAuth не гарантирует такой же доступ, как CI_JOB_TOKEN |

Credentials хранить в поддерживаемом локальном хранилище/защищённых переменных, не печатать и не переносить личный OAuth в deploy secret. Ошибку polling (DNS, timeout, 5xx) сохранять отдельно от состояния pipeline: неизвестный статус не означает failed. После восстановления связи повторно прочитать тот же pipeline ID и SHA.

Runner проверять до большого приложения. Shell executor исполняет jobs на хосте; доступ к Docker daemon даёт высокие права. Для выделенного учебного runner задать привязку к проекту, protected/tagged jobs, политику paused и допустимый код; не давать непроверенному MR доступ к production. Согласовать этот scope один раз и переиспользовать разрешение без рутинных вопросов. При расширении доверия нужна отдельная оценка.

Если `prepare environment` падает до script, читать профиль выделенного пользователя, включая `.bash_logout`/`clear_console`; не считать это дефектом приложения. Исправление профиля в теме 25 закрепить Ansible и повторить настоящий job. [Загрузка shell profile](https://docs.gitlab.com/runner/shells/#shell-profile-loading).

С VM проверить исходящий доступ к GitLab API, Git, registry и фактическим CDN артефактов/образов. Список endpoints сверить с выбранной платформой; один `gitlab.com` не покрывает все загрузки. Временный диагностический SSH-маршрут через ноутбук ограничить loopback/нужными адресами и портами, сохранить TLS и описать удаление. Такой маршрут не доказывает автономность VM; штатный вариант должен работать после отключения ноутбука.

## Контекст CI lint и два разных отказа

Для уже опубликованной конфигурации использовать точный SHA, включая `include:local` файлы, отсутствующие в main. Пример пути API, вызов выполняется настроенным аутентифицированным клиентом без токена в тексте:

```text
GET /projects/<id>/ci/lint?content_ref=<SHA>&include_jobs=true
```

При simulation добавить `dry_run=true` и нужный `dry_run_ref`; POST с текстом конфигурации имеет другой набор параметров. Сохранить method, SHA и контекст. Ошибка вызова API не доказывает ошибку YAML. [CI Lint API](https://docs.gitlab.com/api/lint/).

1. На известном исправном SHA сломать одно заранее названное правило теста. Получить настоящий failed job, JUnit даже при падении и отказ merge. Сохранить commit/pipeline/job, expected/actual; исправить и повторить.
2. Отдельно сломать сборку, например COPY отсутствующего lockfile: тесты проходят, build падает, merge запрещён. Исправить без `allow_failure`, повторить и получить digest. Это не тот же опыт, что падающий тест.
3. Проверить MR и основную ветку. Protected переменная ограничивает контексты выдачи, masked скрывает значение в логах в пределах возможностей GitLab; эти свойства не взаимозаменяемы. Для проверки присутствия использовать безопасный несекретный маркер или boolean, не дамп окружения.
4. Артефакты диагностики очищать от cookies, токенов, runner hints и query подписанных URLs. Искать известные секреты в ограниченном наборе файлов и явно назвать границы проверки, не заявлять «секретов нигде нет» по трём строкам поиска.

При Compose interpolation проверить `docker compose config --quiet` с нужными файлами и безопасными значениями; не выгружать разрешённый конфиг с секретами в общие artifacts. В YAML flow-списках строки с `${...}` или запятыми в mount options заключать в кавычки.

## Дополнение pipeline по мере курса

При добавлении обязательного job проверить DAG `needs`, а не только порядок `stages`. Учебный негативный пример: deploy с `needs: [build]` может обойти новый gate. Исправление должно требовать новый gate; подтвердить отказом до deployment и timestamps jobs после исправления. В теме 12 это проверка тестового артефакта; цепочка `helm-integration → staging → production` возникает только в теме 28.

В теме 26 описать allowlist параметров deploy. Переменные из родительского CI/ноутбука не должны незаметно менять управляемые `UI_PORT`, `STATIC_DIR`, имя БД или overlays. Негативный тест передаёт неожиданные overrides и проверяет безопасный отказ/игнорирование по контракту; сравнивать несекретные итоговые параметры, не печатать `env`. Проверить точный digest, runtime smoke и блокировку production при отказе staging.

## Remote state до платных ресурсов: тема 24

В отдельном учебном каталоге и отдельных именах state использовать `terraform_data` без облачного provider. Это проверка state и переноса plan, не развёрнутые staging/production VM. Пример исходной конфигурации:

```hcl
terraform {
  required_version = ">= 1.4, < 2.0"
  backend "http" {}
}
resource "terraform_data" "probe" {
  input = "orderflow-state-lab-v1"
}
```

Перед запуском выбрать и закрепить фактически проверенную версию CLI в паспорте. Endpoint, lock/unlock методы и credentials задать через окружение backend; не передавать пароль через `-backend-config` и не включать его в HCL. Binary plan может содержать чувствительные данные: ограничить доступ/срок артефакта, проверить содержимое локально через `terraform show -json` без публикации полного вывода. [HTTP backend](https://developer.hashicorp.com/terraform/language/backend/http).

Пример только для GitLab CI job того же учебного проекта, с заранее заданным несекретным `COURSE_STATE_NAME`. В другом job используется его собственный CI_JOB_TOKEN; не сохранять токен предыдущего job внутри plan. Для локального запуска отдельно настроить поддерживаемую identity и проверить права — не подставлять неизвестный личный OAuth автоматически.

```sh
export TF_HTTP_ADDRESS="${CI_API_V4_URL}/projects/${CI_PROJECT_ID}/terraform/state/${COURSE_STATE_NAME}"
export TF_HTTP_LOCK_ADDRESS="${TF_HTTP_ADDRESS}/lock"
export TF_HTTP_UNLOCK_ADDRESS="${TF_HTTP_ADDRESS}/lock"
export TF_HTTP_LOCK_METHOD=POST
export TF_HTTP_UNLOCK_METHOD=DELETE
export TF_HTTP_USERNAME=gitlab-ci-token
export TF_HTTP_PASSWORD="$CI_JOB_TOKEN"
terraform init -input=false
```

Сверить доступность state и права job для своей редакции GitLab по [инструкции managed state](https://docs.gitlab.com/user/infrastructure/iac/terraform_state/). Это настройка среды, не разрешение apply; вывод shell tracing с credentials отключён.

MR делает init/validate/plan, apply в MR отсутствует. Защищённый apply получает тот же сохранённый plan в другом job и не пересчитывает его незаметно; stale plan отклоняется. Проверить авторизованный read, отказ анонимного чтения, конкурентную блокировку, затем освобождение и успешный повтор. Различать ID владельца lock и неуспешной попытки; не force-unlock чужой живой процесс.

После опыта удалить только синтетические ресурсы согласованным destroy и независимо прочитать пустой state/serial; затем обработать хранение самого state по политике проекта. При недоступном remote backend локальный plan делать в отдельной рабочей копии с явно локальным backend, без потери удалённого state. Он подтверждает только локальную часть. Переход к remote — отдельная проверяемая миграция после восстановления доступа.
