# Подготовка и восстановление учебной среды

Редакция: 2026-10-06. Читать нужный раздел перед первой практикой в новой среде и после паузы. Здесь порядок диагностики; команды с именами-примерами сначала привязать к реальному стенду. Выполнение за ученика возможно в пределах уже выданного разрешения.

## Выбор минимальной среды

| Этап | Нужен стенд | Если его нет |
| --- | --- | --- |

| 27–29 | Изолированный локальный кластер и хранилище копий | Проверить ресурсы и версии; render не заменяет кластер |

Для нового стенда составить паспорт: ОС/архитектура хоста и VM, версии Python/Docker/Compose, репозиторий и commit, требуемые службы, схема портов, путь данных, доступные CPU/RAM и диск, владелец ресурсов, команда запуска/проверки/остановки. На macOS ARM отдельно проверить платформы образов и Python-пакетов; успешная эмуляция x86 не означает нативную совместимость. Не менять глобальный Python ради одного курса: использовать отдельное окружение.

Для изолированных упражнений доступны два автоматизированных профиля: [PostgreSQL/RabbitMQ](../assets/backend-labs/README.md) для 07/08/17 и [Linux/kind](../assets/labs/BOOTSTRAP.md) для диагностических лабораторий systemd/Ansible/Terraform/Kubernetes. Каждый имеет doctor/setup/check/stop/resume, собственный инвентарь и сохраняет данные. Эти профили не закрывают SSH/reboot VM, облачные права или весь стек OrderFlow; использовать только на соответствующем этапе.

### Preflight без изменения ресурсов

Запускать команды только там, где инструмент уже установлен. Сохранять краткий безопасный вывод, а не все переменные окружения.

```sh
uname -sm
python3 -c 'import platform,sys; print(sys.version.split()[0], platform.machine())'
df -h .
docker version
docker system df
docker compose version
```

На Linux проверить `free -h`, `ss -ltn` и файловую систему с Docker data-root; на macOS — свободное место тома с Docker disk image и лимиты диска/RAM в Docker Desktop. `docker system df` показывает занятый объём Docker, не свободное место хоста. Сравнить занятые порты со схемой; не останавливать чужой процесс ради лаборатории.

В паспорте заранее задать запас диска для pull, распаковки, сборки, БД и writable layers. Даже кешированный образ требует места при старте. Для небольшого учебного стека запас 3–5 GiB — лишь пример нижнего порога, не рекомендация для Kafka/ClickHouse или всего курса. Измерять рост выбранного профиля; при недостатке ресурса остановить подготовку до новых start/build.

Записывать один повторяемый маршрут: чистая копия → установка по lockfile → минимальные данные → проверка. `.env.example` содержит имена и безопасные placeholders. Приватный `.env`, volumes, state и дампы не входят в исходный комплект. Для сброса создать отдельное имя Compose project/VM/namespace и инвентарь его ресурсов. Сначала остановка и диагностика, затем адресное восстановление; удаление данных — отдельное явно выбранное действие. Команды общего prune не являются сбросом учебного стенда.

### Схема для темы 10

Учебные номера портов, не обязательные настройки проекта. До запуска проверить, свободен ли host port; БД не публиковать наружу без отдельной необходимости.

```mermaid
flowchart LR
    Client["Клиент на хосте"] -->|"127.0.0.1:18090"| Port["Публикация порта"]
    subgraph Compose["Отдельная сеть Compose"]
        Port -->|"app:8000"| App["Процесс Django"]
        App -->|"db:5432"| DB["PostgreSQL"]
    end
    DB --> Volume["Именованный том данных"]
```

Ожидаемые состояния: после запуска доступен API; после recreate app запись остаётся; после recreate db с тем же томом запись остаётся; остановка контейнера не означает удаление тома. Host port, внутренний port и имя сервиса — разные элементы пути. Redis появится на этой схеме в теме 16 после изучения кеша.

### Linux и bootstrap: темы 02, 11, 24

1. Проверить вход по ключу, fingerprint хоста и отдельного пользователя; не отключать проверку host key. Зафиксировать фактические units через `systemctl list-unit-files 'ssh*'`: на конкретном образе SSH может запускаться через socket, а имя службы отличаться.
2. Перед изменением SSH проверить `sudo sshd -t`, сохранить действующее соединение и проверить новое. Не выполнять reload неактивной `ssh.service` вслепую и не открывать SSH всему Интернету как универсальное исправление.
3. Для службы отдельно проверить `systemctl is-active <unit>`, `systemctl is-enabled <unit>`, журнал, PID, пользователя и порт. Enabled не равно работает; `Restart=on-failure` не исправляет неверный ExecStart.
4. До согласованного reboot сохранить `/proc/sys/kernel/random/boot_id`; после нового входа сверить новый boot ID, состояние службы и реальный HTTP. Только повторная проверка завершает опыт автозапуска.
5. При cloud-init сначала `cloud-init status --long` и относящийся к сбою журнал. Действия once-per-instance не повторятся от одного restart `cloud-final`. После исправления повторять выбранный модуль с понятными последствиями, например `cloud-init single --name <нужный-модуль> --frequency always` на изолированной VM. Не применять полную очистку cloud-init ради одного шага: она может повторить настройку доступа. [Официальный порядок повторного запуска](https://docs.cloud-init.io/en/latest/howto/rerun_cloud_init.html).

### Диагностика HTTP/TLS: темы 03 и 11

Пример чтения публичного учебного адреса; заменить URL, не добавлять пароль в командную строку. Во втором действии сразу получить код первого, не потерять его за пайпом:

```sh
curl --silent --show-error --output /dev/null --max-time 10 \
  --write-out 'http=%{http_code} dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} total=%{time_total}\n' \
  https://example.org/
printf 'curl_exit=%s\n' "$?"
```

Тайминги curl накопительные; разности дают длительность отдельных фаз. Без `--fail` HTTP 403 может сопровождаться exit 0. Сначала различать DNS, TCP, TLS и HTTP, затем объяснять отказ. Для своего нестандартного порта проверить полный Origin со схемой и портом и корректный Host. Для конкретного IP сохранять имя сертификата через `--resolve`, если это нужно сценарию. Отдельно проверять имя, срок и доверенную CA; `-k` не является доказательством исправного TLS. Коллекция содержит успешный запрос, неверный ввод, разрешённый и чужой Origin по контракту, а не только один healthcheck.

## Облако: до создания платных ресурсов

Провайдер выбирается по доступности из реальной сети/VPN, поддержке нужных ресурсов и стоимости; Yandex Cloud — один из примеров, не обязательная платформа. Проверить отдельно web-консоль, аутентифицированный API и SSH-маршрут. Анонимный HTTP 200 консоли не подтверждает права API. Идентификатор каталога/проекта сохранить один раз: он не является credential и не доказывает роль пользователя.

При 401/403 записать безопасные endpoint, операцию, status и request ID; определить, известна ли identity и доступен ли нужный scope. Не угадывать причину только по числу 403, не просить токен в чат. Вход делать локально через поддерживаемый CLI/secret store. Уже подтверждённые данные не запрашивать заново.

Перед apply заполнить датированный расчёт по официальным тарифам выбранного региона:

| Ресурс | Количество/размер | Тариф и ссылка, дата/валюта | Период | Сумма |
| --- | --- | --- | --- | --- |
| VM CPU/RAM | <конфигурация> | <за час> | <активные часы> | <расчёт> |
| Диск | <GiB> | <за GiB-месяц> | <календарное хранение> | <расчёт по правилам провайдера> |
| IP, snapshots, object storage | <объём/адреса> | <тарифы и минимумы> | <в том числе пауза> | <расчёт> |
| Трафик, операции, CI/registry | <допущения> | <тариф/доступная квота> | <период> | <резерв> |

Согласовать предел и период затрат, дату остановки/удаления, сохраняемые данные и scope доступа. Уведомление бюджета может не останавливать расходы автоматически. Остановка VM не обязательно прекращает оплату диска/IP/хранилища. При паузе показать фактические оставшиеся ресурсы и оценку их хранения; не удалять единственную копию ради экономии.

До создания проверить квоты сети, VM, CPU, дисков и IP, региональные ограничения и права. Альтернатива новой сети — явно выбранная существующая сеть как data source, без присвоения её жизненного цикла лаборатории. После частичного apply не повторять исходный план вслепую: прочитать state и cloud inventory, установить, что уже создано, сформировать новый plan и оценить только остаток. Не терять state и не выполнять destroy чужой сети.

Негативные IAM-проверки выполнять на отдельном disposable объекте: identity, разрешённый GET/LIST/PUT по роли, ожидаемо запрещённый DELETE. Не проверять DELETE на единственной резервной копии и не расширять права, чтобы скрыть ожидаемый отказ. Отсутствующее поле API не равно пустому: проверить полную проекцию/другой документированный endpoint; fallback через provider refresh назвать отдельным источником доказательства.

## Контроллер Ansible: тема 25

До playbook проверить архитектуру Python, место под зависимости, SSH той же identity и длину локального пути control socket. При длинных путях на macOS использовать короткий принадлежащий пользователю каталог с режимом 0700 и параметр `control_path_dir` из [настроек SSH connection](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/ssh_connection.html). Пример настройки после создания такого каталога:

```ini
[ssh_connection]
control_path_dir = /tmp/of-ansible-<индивидуальное-имя>
```

Не использовать общую доступную всем папку и не отключать host key checking. Сетевое разрешение, если нужно инструменту, ограничить выбранным inventory/серией проверок. Уже разрешённые повторы не требуют новых вопросов; новый платный ресурс или расширение доступа обсуждаются отдельно.

## Восстановление после ENOSPC

Не повторять start при недостатке места. Сохранить доступные логи и список контейнеров/томов; при недоступном daemon состояние обозначить неизвестным. После адресного освобождения согласованных временных файлов восстановить Docker, заново проверить оба диска и проверить persistent volumes. Только затем пересоздавать повреждённый контейнер без удаления тома и проверять данные/realm/MFA. EOFException сам по себе не доказывает повреждение БД или причину усечения файла. Не выполнять общий prune, `down -v` или удаление realm как первый шаг.
