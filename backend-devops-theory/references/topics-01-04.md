## 01 Проектирование продукта и организация разработки

Вся тема: 12 часов. Предпосылки: Основы Python уже известны. Основа: Б с. 6; М с. 4, 6; Д с. 4, 11.

**Охват теории:** Границы MVP, пользовательские сценарии, функциональные и эксплуатационные требования. Модульный монолит, Git и небольшие merge requests. Типизация публичных функций, pyproject.toml, фиксация зависимостей, линтер и форматирование.

**Выдавать по частям:**
1. Требования к OrderFlow, MVP и критерии результата.
2. Модульный монолит и границы ответственности.
3. Git, маленький MR, окружение и качество кода.

**Контекст будущей практики:**
- Создать репозиторий OrderFlow и backlog для покупателя, оператора и администратора. Описать создание, просмотр и отмену заказа.
- Выделить модули catalog, carts, orders и users; завести README, .env.example, команды установки и проверки кода.
- Записать первое архитектурное решение: почему стартуем с Django и какие компоненты можно выделить позже. Оформить первый MR.

**К чему готовить объяснение:** Из чистого клона воспроизводится установка; проверки запускаются одной командой; секретов нет. Для каждой задачи MVP записан наблюдаемый результат.

**Фокус последующего ревью:** Проверить границы задачи, понятность структуры, воспроизводимость окружения и размер MR. Убрать преждевременные абстракции; после замечаний обновить код и документацию.

**Постановка и интеграция:** Использовать [карточку задания](practice-review.md): история → критерий → проверка, версия исходника, fixture и область typecheck. В README дать одну команду установки и одну проверки из чистой копии без локальных runtime/env/cache. Вход в GitLab отделить от выбора URL проекта: существующий учебный репозиторий подходит, отдельный приватный нужен только при выбранной изоляции. Backlog вести в Markdown или доступной доске, без обязательного trial. После темы 04 связать контракт, схему и первое ADR в [интеграционном занятии](course-delivery.md).

## 02 Linux Bash и диагностика окружения

Вся тема: 16 часов. Предпосылки: 01. Основа: Д с. 5; Б с. 10.

**Охват теории:** Файлы и права, пользователи, процессы, сигналы, память, диски, пакеты, systemd и journald. Bash: аргументы, кавычки, потоки вывода, коды возврата, обработка ошибок и очистка ресурсов.

**Выдавать по частям:**
1. Процессы, пользователи, права и служба приложения.
2. Bash, аргументы, потоки и обработка ошибок.
3. Диагностика CPU, памяти, диска и портов.

В 02/1 сначала объяснить ключи SSH, проверку fingerprint и пользователя службы. До практики предоставить доступный Linux; его платное создание и облачная автоматизация не являются предпосылками части. Локальный диагностический контейнер закрывает только явно проверенные процессы/systemd, не SSH и reboot VM.

**Контекст будущей практики:**
- Подготовить Linux VM, настроить SSH по ключу и отдельного пользователя приложения.
- Написать scripts/diagnose.sh: CPU, память, диск, процессы приложения, открытые порты и состояние службы.
- Разобрать три поломки на учебной VM: занятый порт, неверные права и неработающая служба. Описать путь от симптома к причине.

**К чему готовить объяснение:** Скрипт возвращает ненулевой код при критической ошибке, корректно обрабатывает путь с пробелами и не печатает секреты. Все три неисправности воспроизводятся и устраняются.

**Фокус последующего ревью:** Проверить quoting, обработку ошибок, права и безопасный повторный запуск. Попросить объяснить выбранные диагностические команды и исправить ненадёжные участки.

**Подготовка и диагностические задания:** До команд проверить Linux VM по [паспорту среды](environment-guide.md); macOS/контейнер без systemd не заменяет этот стенд. Использовать L02a–c из [банка неисправностей](fault-labs.md): чужой процесс не останавливать, проверять права всего пути. Показать различие active/enabled, socket-activated SSH и `sshd -t`. Для своего сервиса проверить новый boot ID и HTTP после согласованного reboot; облачный bootstrap отложить до темы 24.

## 03 HTTP сети и контракт API

Вся тема: 14 часов. Предпосылки: 01, 02. Основа: Б с. 7, 9; Д с. 5, 8.

**Охват теории:** DNS, TCP, TLS, порты, HTTP-методы и статусы, заголовки, JSON, cookies, CORS. REST, идемпотентность, OpenAPI, единый формат ошибок. На коротком примере Flask: маршруты, валидация и обработка исключений.

**Выдавать по частям:**
1. Путь запроса через DNS, TCP, TLS и HTTP.
2. REST, контракт OpenAPI, статусы и идемпотентность.
3. Валидация и ошибки на примере Flask-эмулятора.

Для 03/1 преподаватель предоставляет готовый HTTP/TLS endpoint и контролируемые отказы. Написание Flask-эмулятора требуется лишь в 03/3, а не до объяснения сетевого запроса.

**Контекст будущей практики:**
- Описать OpenAPI для каталога, корзины, заказа и отмены; зафиксировать схемы запросов, ответов и ошибок.
- Создать на Flask учебный эмулятор службы доставки: расчёт цены, задержка ответа и управляемая ошибка. Он пригодится для будущих интеграций.
- Пройти запрос через curl и разобрать DNS, соединение, TLS и ответ. Добавить коллекцию запросов с корректными и некорректными данными.

**К чему готовить объяснение:** Контракт различает ошибки валидации, доступа, конфликта состояния и внешнего сервиса. Эмулятор детерминированно возвращает заданный сценарий.

**Фокус последующего ревью:** Проверить семантику методов и статусов, границы входных данных, совместимость схем и отсутствие утечки внутренних исключений. Исправить неоднозначности контракта.

**Материалы практики:** Перед интеграцией выполнить малые HTTP-упражнения 03/1 и 03/3 из [маршрута](course-delivery.md). В коллекции сохранить exit/status и DNS/TCP/TLS/HTTP-тайминги, корректный Host/Origin с нестандартным портом; TLS name/expiry/CA проверять отдельно, без зачёта по `-k`. [Порядок диагностики](environment-guide.md) и [контракт v1](business-contract.md) дают исходные условия; реализация конкуренции появится в теме 08.

## 04 SQL и проектирование PostgreSQL

Вся тема: 22 часов. Предпосылки: 01, 03. Основа: Б с. 7; М с. 5; Д с. 10.

**Охват теории:** Нормализация, ключи, ограничения и связи. SELECT, JOIN, GROUP BY, подзапросы, CTE и оконные функции. NUMERIC для денег, временные зоны, индексы и основы транзакций.

**Выдавать по частям:**
1. Модель данных, связи, ограничения, деньги и время.
2. SQL, JOIN, группировки и агрегаты.
3. CTE, подзапросы, оконные функции и основы индексов.

**Контекст будущей практики:**
- Спроектировать таблицы пользователей, товаров, остатков, корзин, заказов, позиций и истории статусов. Зафиксировать цену товара в позиции заказа.
- Написать DDL и генератор синтетических данных. Запретить отрицательные остатки и количество, задать уникальность артикулов.
- Составить запросы по обороту, популярным товарам и заказам пользователя; реализовать одну сводку с оконной функцией.

**К чему готовить объяснение:** Схема создаётся на пустой PostgreSQL; неверные данные отвергаются ограничениями. Отчёты совпадают с заранее рассчитанными результатами на малом наборе.

**Фокус последующего ревью:** Проверить кардинальности, типы, ограничения, удаление связанных данных и обоснование индексов. Устранить расхождения между схемой и требованиями заказа.

**Контрольные данные:** Использовать [малый SQL-набор](business-contract.md): несколько позиций, несколько возвратов одной позиции, заказ без возврата и заранее рассчитанные итоги. Возвраты здесь лишь входная таблица упражнения на JOIN, без реализации процесса темы 30. Сначала ученик считает результат вручную, затем пишет запрос; сравнение упорядочено по ключу. На итоговом занятии 01–04 проверяющий повторяет установку и запросы, ученик объясняет кардинальности и альтернативу схеме.
