## OrderFlow

Объяснять материал на backend сервиса заказов интернет-магазина. Покупатель управляет своей корзиной и заказами; оператор обрабатывает заказы; администратор управляет каталогом и доступом. Использовать синтетические данные, эмуляторы оплаты и доставки. Не предполагать существование рабочего репозитория или уже написанного кода, пока пользователь его не предоставил.

Начинать с модульного Django-приложения, затем выделять доставку на FastAPI и фоновые обработчики. Использовать Flask для учебного внешнего API, а не переписывать один продукт на трёх фреймворках. Вводить инфраструктуру по мере задач, не требовать запускать весь стек для первого урока.

| Компонент | Ответственность |
| --- | --- |
| Django и DRF | Каталог, пользователи, корзины, остатки, заказы и история статусов |
| PostgreSQL | Основные данные продукта; для доставки отдельная БД либо изолированная схема и роль |
| FastAPI | Предложения доставки и её оформление, собственный контракт и миграции |
| SQLAlchemy и Alembic | Асинхронный доступ и миграции сервиса доставки |
| Redis | Кеш публичных данных, с явной политикой устаревания и поведения при отказе |
| Celery и RabbitMQ | Фоновые задачи и уведомления; outbox связывает транзакцию и намерение публикации |
| Elasticsearch и ETL | Поисковая проекция каталога с повторяемой загрузкой |
| Kafka и ClickHouse | Поток событий, аналитика и повторный расчёт |
| GitLab CI и контейнеры | Проверки, сборка, доставка неизменяемого артефакта |
| Terraform и Ansible | Инфраструктура и конфигурация учебных серверов |
| Kubernetes и Helm | Развёртывание, обновление, ресурсы, масштабирование и политики |
| Prometheus Grafana Loki OpenTelemetry | Метрики, логи, трассы, алерты и диагностика |

## Правила продукта

- Хранить деньги в точном представлении; фиксировать цену в позиции заказа; вычислять итог на сервере.
- Создавать заказ и резервировать остаток атомарно; проверять гонку за последнюю единицу товара.
- Для одинаковых ключа идемпотентности и тела запроса возвращать исходный результат; для другого тела с тем же ключом возвращать конфликт.
- Разрешать только определённые переходы статусов: new, confirmed, shipped, completed; явно определить допустимость отмены. Хранить историю.
- Проверять доступ к конкретному объекту, а не доверять присланному user_id или номеру заказа.
- Отделять отказ уведомления или аналитики от успешности заказа. Для недоступной доставки определять промежуточное состояние и повтор действия.
- Изменять данные только через их владельца. Считать поиск и аналитику проекциями с отдельным порядком обновления и восстановления.
- В итоговой теме добавить частичный возврат с идемпотентностью и эмулятором денежной операции.

Для согласования конкретных входов/выходов использовать [пример контракта и контрольные SQL-данные](business-contract.md). Он версионируется в задании и не меняет уже принятую сдачу задним числом. Возврат и долговечный платёжный эмулятор относятся к теме 30; их нельзя требовать от начального API.

## Связь теории с обучением

Для каждой темы программой предусмотрены практика, критерии приёмки, ревью и исправления. Этот skill выдаёт объяснения, задания после частей урока и разбирает понимание материала. Использовать практику из спецификаций как основу задания, а не как команду выполнить реализацию за пользователя.

Опираться на явные пользовательские сведения о прогрессе. Отсутствие замечаний пользователя не означает освоение темы, выполненное задание или успешное ревью.

Python с нуля, игры, подробная вёрстка/React и карьерный трек не входят в основной курс. Парсинг, MongoDB, Spark, Protobuf/Avro, масштабирование данных и работа с ИИ находятся в факультативах.
