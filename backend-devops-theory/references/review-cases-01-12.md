# Контрпримеры для тем 01–12

Редакция 2026-10-12 по F02–F18 полного прогона. Читать только раздел своей темы. Это уточнения существующих заданий: выбрать связанные с текущей частью проверки и включить их в карточку **до** попытки. В уже выданном задании новый критерий оформлять дополнением. Намеренная ошибка учебной сдачи не означает дефект исходного курса.

## 01/3, 02/2: отказ проверяющей команды (F02)

У команды «проверить всё» тоже есть контракт. Дать три дочерних процесса с exit 0/7/0 и заранее выбрать fail-fast либо накопление ошибок. При fail-fast третий не запускается, общий exit равен 7, сообщения общего успеха нет. При накоплении третий выполняется, но итог всё равно ненулевой. Проверить путь с пробелом и отсутствие запуска при import. Успешный typecheck этого поведения не подтверждает. В12 этот же принцип связывается с gate pipeline.

## 02: настройка и время наблюдения (F03, F04)

L02a принимает `current`, намеренно отсутствующий `pythno` либо абсолютный путь к существующему исполняемому интерпретатору. Неизвестное имя должно дать ошибку конфигурации до создания unit; нельзя молча подменять путь. Допустимые варианты находятся рядом с выданным config. Учебная поломка ExecStart и ошибка формата настройки имеют разные результаты check:1 и 2.

После `systemd-run --collect` короткая transient-служба уже могла исчезнуть. Поздние inactive/ExecMainStatus=0 не отменяют более ранний exit127 в журнале. Сохранить время start/status/journal/cleanup и разбирать причину по наблюдению во время сбоя. L02c возвращает права каталога в finally для уборки: послесловие cleanup не выдавать за права в момент неудачного open.

## 03/1: TLS после паузы (F05)

Преподаватель предоставляет [TLS fixture](../assets/network-lab/README.md), не поручая ученику Flask/Django до 03/3. Prepare создаёт новый CA, действующий и истёкший leaf относительно текущего UTC. Проверка различает отказ доверия CA, неправильное имя, истёкший leaf и TLS-успех с HTTP 403. Используется явный CA для отдельного запроса без системной установки; `-k` не закрывает TLS-критерий.

После паузы проверить паспорт сертификатов и идентичность живого endpoint. Устаревший ready-файл не подтверждает готовность. Если срок истёк, остановить свой fixture и подготовить новый каталог; старое evidence сохранить. Private keys остаются в собственном 0700 каталоге с 0600 файлами.

## 03/2–3, 05 и 06/1: число до преобразования (F06, F08)

В03 объявить числовой договор; в 05 зафиксировать известное расхождение, если REST ещё вне задания; в 06 проверить настоящий parser→serializer→HTTP. Для математически целого положительного quantity:

| Исходный JSON | Ожидание |
| --- | --- |
| `1`, `1.0`, `1e0` | Одно и то же допустимое количество |
| `true`, `"1"`, `1.5`, `-1` | Отказ |
| `1.0000000000000001`, `1e-10000` | Дробь, отказ до округления |
| `1e10000` | Выход за согласованный диапазон, отказ до создания огромного int |

JSON Schema `integer` описывает математическую целочисленность; одна эта запись не запрещает десятичную точку. Если требуется ограничить исходную запись числа, это дополнительный договор и отдельная проверка. [Числа в JSON Schema](https://json-schema.org/understanding-json-schema/reference/numeric).

`int(data)` принимает лишние типы и обрезает дробь; `float.is_integer()` после округления уже не видит потерянную часть. Для выбранного точного договора сохранить Decimal при JSON-разборе, исключить bool/строки/non-finite и проверить диапазон до int. Проверяющий schema также не должен терять точность. Разобранный малый пример: [numeric_contract.py](../assets/examples/numeric_contract.py); он не заменяет HTTP-тест сериализатора OrderFlow и не навязывает Decimal каждому API.

Тип столбца не проверяет исходную лексему: в PostgreSQL явное `1.5::bigint` округляется до 2, `1.235::numeric(5,2)` — до 1.24. Различать JSON→валидацию→преобразование→хранение; [числовые типы PostgreSQL16](https://www.postgresql.org/docs/16/datatype-numeric.html).

## 04/2: одинаковые суммы разных позиций (F07)

К базовому набору [контракта](business-contract.md) добавить вариант: две разные позиции стоят по 200, возвраты всего 300. Правильный gross400/refund300/net100. `SUM(DISTINCT quantity*price)` ошибочно даёт 200/300/−100, хотя может пройти пример с разными стоимостями. Сначала агрегировать возвраты по item_id, затем складывать позиции. Сохранить и заказ без возвратов; ручной эталон зафиксировать до SQL.

## 07/1: отзыв сессии (F09)

Последовательность приёмки: login → me200 → скопировать cookie в отдельный клиент → logout → старый cookie получает согласованный отказ 403 → новый login снова работает. Проверить server-side отзыв сессии. Ответ logged_out200, AuditEvent и очищенный cookie только исходного клиента недостаточны. Тест хранит credential в памяти; в отчёте только статусы и признаки отзыва.

## 08/3: эффект, ответ и реальная конкуренция (F10, F11)

Два одновременных одинаковых запроса должны дать один заказ и одинаковые первоначальные статус/тело, например 201/201. Итог 201/500 при одной строке защищает эффект, но нарушает договор повтора: отдельно проверять обе стороны. Конфликт другого digest и область actor/key проверяются своим случаем.

Фиксировать две сессии PostgreSQL, backend PID и trace чтения/записи либо `pg_blocking_pids`. Внешний Barrier перед вызовом функции не доказывает пересечения критической секции. Не ставить обязательный двусторонний Barrier после `SELECT FOR UPDATE` одной строки: второй участник правильно ждёт lock и никогда до него не дойдёт. Gate теста освобождается после обоих чтений **или** подтверждённого peer-lock wait; deadline ограничивает ошибку самого опыта.

## 09: зелёные тесты без независимого эталона (F12)

| Слабый тест | Пропущенная ошибка | Исправленная проверка |
| --- | --- | --- |
| Владелец читает свой заказ | Чужой доступ разрешён | Другой actor,403 и неизменное состояние |
| Ответ равен сумме из того же расчёта ORM | И ответ, и БД ошибаются одинаково | Ручной итог 2598 вместо 2599 по fixture |
| stock≥0 | Резерв не выполнен | Было 5, заказ 2, стало ровно 3 |

Schema-valid число может быть неверной суммой. Запустить исходные тесты на baseline и трёх известных мутантах, затем усиленные на тех же копиях. Падение должно происходить в проверяемом поведении, не при setup/import. Обнаружение этих трёх дефектов не даёт общей оценки качества тестов.

## 10: слой образа и маршрут с хоста (F13, F14)

Показать Dockerfile с COPY синтетического canary и последующим rm: финальный контейнер файл не видит, прежний слой image archive содержит байты. После COPY allowlist/.dockerignore повторить просмотр всех слоёв, config/history. Настоящие credentials для опыта не брать. Отсутствие одного canary не доказывает отсутствие всех секретов и не заменяет CVE-проверку.

Сохранять цепочку: YAML разобран → контейнер создан → effective port binding/network из inspect → HTTP с хоста → данные пережили пересоздание. `compose config --quiet`, requested PortBindings и внутренний healthy не заменяют следующие шаги. Ошибки parsing/mount, публикации и неверного targetPort различать; особенности internal network привязывать к версии Engine.

## 11: паспорт стенда и приватный open (F15, F16)

Стабильный паспорт вне временного management-каталога содержит полный ID ресурса, marker/владельца, версию bootstrap, путь управления и адресную остановку. При пропаже inventory сверить сохранённый ID и live marker; совпадение имени не разрешает новый setup поверх ресурса. Отсутствующее управление обозначить как отсутствующее.

Проверять private env/key настоящим открытием под UID worker, перенаправляя содержимое в /dev/null. Записать stat каждого родителя и файла **внутри Linux**, UID и тип storage; public CSS должен читаться. Host chmod600 на Desktop bind не доказывает запрет внутри контейнера. Если отображение владельца мешает опыту, использовать свой root-owned Linux volume/tmpfs, а не открывать весь deployment рекурсивно.

## 12: gate по времени и источник pipeline (F17, F18)

Сохранить started_at/finished_at gate и marker. Failed pipeline недостаточен: marker мог успеть выполнить действие до старта gate. В исправлении marker skipped после failed gate, а после successful gate стартует позже его завершения. Локальная DAG-модель и настоящий hosted pipeline оцениваются отдельно.

Матрица rules включает source и ref: push/main, push/feature, merge_request_event, tag и schedule/main. Условие branch==default_branch само по себе не ограничивает source до push. Локальная модель пары условий не заменяет GitLab parser и не считается настоящим scheduled запуском. [Источники pipeline](https://docs.gitlab.com/ci/jobs/job_rules/#ci_pipeline_source-predefined-variable).
