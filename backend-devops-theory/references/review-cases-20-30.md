# Контрпримеры для тем 20–30

Редакция 2026-10-12 по F32–F47. Эти проверки конкретизируют согласованные критерии текущей части. Применять их к своему стенду; не добавлять платный сервис, инфраструктурный проект или скрытое требование после сдачи.

## 20: небольшой индекс до большого опыта (F32)

После проверки диска выполнить в собственном индексе create → active primary → write → refresh/search/count → delete. HTTP health пустого Elasticsearch не доказывает возможность allocation. При timeout сохранить allocation/explain, unassigned shards и фактические watermarks/free bytes. Это может быть ошибка подготовки, а не поиска/ETL. Для малого ограниченного стенда пороги объявляются явно; отключение disk protection и очистка чужих ресурсов не являются исправлением. [Disk allocation](https://www.elastic.co/docs/reference/elasticsearch/configuration-reference/cluster-level-shard-allocation-routing-settings#disk-based-shard-allocation).

## 21: независимые границы transport и агрегации (F33)

Сначала проверить настоящий send: key, partition, actor_id и считываемый payload. Отдельный fixture с правильным ключом позволяет дойти до commit/replay/агрегации, если ошибочный producer ломает раннюю проверку. Такой fixture прямо пометить обходом transport, не полным end-to-end доказательством.

Сохранить raw rows, уникальные event_id, значения фактов, оборот и воронку до/после replay. Настоящий crash до подтверждения и после записи имеет разные последствия. Дубли raw при неизменных unique фактах допустимы лишь в объявленной модели; рост оборота при replay — ошибка. Падение маршрутизации не доказывает остальные дефекты consumer.

## 22: загруженная панель и живые процессы (F34–F36)

После изменения dashboard получить его через Grafana API и сравнить нужные expressions, labels и текст runbook. SHA mounted JSON, uid и число панелей недостаточны. Для bind mounts проверить режим watcher/polling; успешный reload ещё требует readback. Периодическое обновление не считать измеренным по одному ручному reload. [Grafana provisioning](https://grafana.com/docs/grafana/latest/administration/provisioning/).

Остановить PG и подать заранее выбранный поток, наблюдая три отдельных сигнала: доступность HTTP handler, доступность counters для scrape и состояние зависимости. Общий занятый HTTP pool может скрыть counters. При отдельном exporter исключить дубли business series в старом target. Подтвердить фактический alert с прежними rate guard/for и получение локальным sink; не снижать пороги, чтобы сделать тест зелёным.

После PG restart сохранить PID/StartedAt долгоживущего dispatcher: он должен восстановиться без собственного перезапуска, обработать pending event и новый checkout, доставить один эффект, а replay не дублирует письмо. Вне request lifecycle Django не очищает connection на границах каждого poll автоматически; разобрать `close_old_connections()` перед попыткой и в finally, а также обработку ошибок/бюджет retry. Один HTTP 200 после восстановления этого не доказывает. [Django persistent connections](https://docs.djangoproject.com/en/5.2/ref/databases/#persistent-connections).

## 23: полнота нагрузки и исправность наблюдателя (F37, F38)

До нагрузки проверить URL метрик, HTTP 200, Content-Type, разбираемый формат и наличие обязательной серии с ожидаемыми labels. HTML 404 сохранять как отказ сборщика, не как counters; отделять валидные client timings от непроверенного серверного канала.

Для before/after сохранять исходное расписание offered journeys, late starts/drops, окно подачи и drain, число допущенных/завершённых запросов, endpoint и journey quantiles, серверный журнал и условия хоста. Выполнить минимум два сравнимых повтора и сохранить оба, включая неудобный результат. Ноль HTTP errors у допущенных запросов не означает 100% выполнения предложенной нагрузки. Сокращение SQL подтверждает механизм оптимизации сильнее, чем единственный удачный p95; оно не доказывает рост общей capacity.

## 24/1 и 25/2: момент выдачи и ложный changed0 (F39, F40)

T24 выдаётся после local plan/apply в 24/1. Она различает exit0/2/1; remote lock, облачный drift и stale plan остаются следующими опытами. Каталог, карта частей и сгенерированный ASSIGNMENT должны называть одну часть.

В авторской проверке A25 дополнительно замаскировать безусловный restart через `changed_when: false`. Первоначальный простой fixture ученика сохраняется. Проверяющий обязан отвергнуть repeat с changed0 при новом PID или изменённом config/HTTP. Исправление через handler проходит повтор без restart, изменение только proxy-шаблона затрагивает только proxy. Зелёный recap не заменяет наблюдение. Авторский вариант и проверка predicate находятся в каталоге и tests; локальная mock-регрессия не заменяет настоящий Linux/Ansible запуск.

## 26 и 27: Unix-доступ и готовый endpoint (F41, F42)

Private bind проверить stat/UID внутри контейнера и настоящим open под worker UID без вывода содержимого; отдельно проверить HTTP 403 и читаемую public статику. Это разные границы. Если Docker Desktop меняет отображение владельца, дать свой root-owned Linux volume/tmpfs с 0700/0600, сохранив прежние данные.

IP может оставаться в EndpointSlice при `conditions.ready=false`. По обычному Service такой Pod не участвует как готовый backend; считать адреса недостаточно. Записать ready/serving/terminating, проверить Service и локальный socket отдельно. Для `publishNotReadyAddresses` и завершающихся endpoints действуют отдельные правила маршрутизации; не переносить обычный случай на них без проверки. [EndpointSlice conditions](https://kubernetes.io/docs/concepts/services-networking/endpoint-slices/#conditions).

## 28: чистая установка и передача replicas (F43, F44)

Проверить Helm install на пустой БД отдельно от upgrade прогретого окружения. `--wait` не задаёт порядок запуска PG и migration Job. Job нужен конечный SQL preflight, повтор с сохранённой причиной первоначального отказа и проверка фактической версии схемы до business smoke. Failed Job и логи сохраняются до cleanup.

Различать первичную установку сHPA и передачу существующего Deployment от Helm кHPA. Проверить rendered spec.replicas, patch/defaulting и live Ready replicas во время передачи. Простое удаление поля может временно привести к default 1, затем HPA восстановит minReplicas. После двух готовых реплик можно измерять нагрузку; такой опыт не подтверждает непрерывный HTTP именно при handoff. Если обещана доступность перехода, наблюдать её отдельно и проверить способ передачи управления для конкретных версий. [Kubernetes: миграция replicas кHPA](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/#migrating-deployments-and-statefulsets-to-horizontal-autoscaling).

## 29: пригодный архив и внешние последствия (F45, F46)

Дать два пригодных backup A/B и корректно зашифрованный, но усечённый dump C. Decrypt/plainSHA и чтение TOC не подтверждают полный restore. В расходной retention-папке показать ошибочный выбор C/B; исправленный отбор опирается на реальный restore, сверку ожидаемых таблиц/данных и exact hashes зашифрованного и открытого кандидата. Изменившийся после проверки файл не сохраняет статус verified. Плохая новая копия не вытесняет последние хорошие; retention собственного задания не разрешает удалять чужие архивы.

Заказ после cutoff мог уже создать внешний SMTP/платёж. Restore удаляет его запись из БД, но не отменяет внешний эффект. Новый заказ может повторно получить тот же числовой PK, имея другой public_reference/event UUID. Сверять внешние идентичности и журнал обязательств; не обещать exactly-once после потери журнала идемпотентности. Потерянные последствия отдельно описать в postmortem. Это граница доказательства восстановления, а не требование автоматически реализовать весь production reconciliation.

## 30: контракт поиска выплаты (F47)

Новый клиент и старый provider без GET могут дать HTML 404. Этот ответ означает неизвестный маршрут, не отсутствие денежной операции. Только предусмотренный контрактом аутентифицированный JSON not_found допускает выбранный путь создания; неверное тело/status, timeout и недоступность сохраняют unknown outcome.

В матрице: GET известного ключа, проверяемый missing,401, malformed response, старый provider, restart ledger. Сверять ключ, сумму, валюту/состояние и идентификатор по договору до записи результата. При неизвестном исходе использовать прежний event UUID; новый случайный key на каждом retry воспроизводит двойную выплату. Проверить независимый ledger, stock, повтор задач, mixed API/worker и rollback. Реальный платёжный сервис с другим контрактом потребует отдельного адаптера; учебный эмулятор не доказывает его поведение.
