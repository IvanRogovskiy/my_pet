# Проверки развёртывания, релиза и восстановления

Редакция: 2026-10-06. Это детализация критериев соответствующих тем. Включать нужные сценарии в задание до начала работы; существующим сдачам не добавлять их задним числом. Обязательные доказательства оформлять по [шаблону ревью](practice-review.md).

## Браузер и публичные файлы: темы 05, 11, 19, 26

В теме 05 проверить в настоящем браузере вход сотрудника, форму и ограничения данных в среде разработки. Производственная раздача статики относится к теме 11: `STATIC_ROOT → collectstatic → Nginx`. Проверить CSS/JS запросы, MIME, отсутствие 404 и реальные действия формы с последующим чтением данных; один HTML 200 недостаточен. Не включать DEBUG/runserver для исправления production-статики. [Развёртывание static files Django](https://docs.djangoproject.com/en/5.2/howto/static-files/deployment/).

После переноса файлов проверить SHA ожидаемых assets, владельца и фактическую возможность чтения под UID веб-сервера в Linux. Для публичного каталога/файла могут подходить 0755/0644, но права должны учитывать весь путь и владельца; `mkdir(mode=...)` ещё зависит от umask. Приватные `.env`, ключи и их каталоги остаются закрытыми, например 0600/0700. Не применять рекурсивное открытие всего deployment. macOS bind mount не заменяет проверку Linux-прав.

В теме 26 статика относится к тому же digest/версии, что и код. После обновления и rollback проверить согласованную пару кода и assets, публичный путь и форму. В отчёте различать «страница открылась», «assets проверены» и «форма отправлена»; локальная форма не доказывает облачную форму.

Для мобильного UI использовать mobile browser context, а не только узкий desktop viewport. Снять метрики viewport/layout/scale и просмотреть снимок: отсутствие overflow не доказывает читаемость цены/кнопок. Целевой размер задаётся заданием, например 390 px; визуальная проверка относится к служебному интерфейсу, не расширяет курс до frontend-разработки.

При недоступности встроенного браузера сохранить точную ошибку инструмента. Допустим отдельный headless-браузер с изолированным профилем и совместимой библиотекой; по возможности использовать уже установленный браузер, не менять глобальные зависимости. HTTP smoke оставить отдельной проверкой. После опыта закрыть созданный профиль и процессы.

В теме 19 browser acceptance проверяет результат: неверный пароль не создаёт сессию, анонимный запрос отклоняется по контракту, верный вход проходит callback и даёт ожидаемую пару issuer/subject, для администратора работает MFA, выход завершает сессию. Ошибка отсутствующего `#input-error` сначала означает дефект селектора, не дефект авторизации. До закрытия браузера собрать этап, класс ошибки, безопасные признаки DOM и статусы запросов. Не сохранять значения полей, HTML с токенами, cookies и callback URL с code/state. Скриншоты также проверить на чувствительные данные.

## Terraform: тема 24

Подготовка — [среда](environment-guide.md) и [отдельный HTTP backend](gitlab-labs.md). Сначала local → remote без платных ресурсов, затем облачный provider. Порядок является частями одной темы, не новым курсом.

Закрепить CLI/provider и lockfile, источник пакетов и checksum. Перед Linux CI проверить наличие поддерживаемой платформы и контрольных сумм для неё; успех darwin_arm64 не подтверждает linux_amd64/arm64. Filesystem mirror и CLI config описать в README; локальная ручная установка не должна быть скрытой предпосылкой.

| Опыт | Действие | Наблюдаемое доказательство |
| --- | --- | --- |
| Изменение HCL | Поменять конфигурацию существующего учебного ресурса | `plan -detailed-exitcode` даёт 2, diff соответствует HCL; это изменение намерения, не внешний drift |
| Внешний drift | В отдельном ресурсе изменить разрешённое поле через API/консоль, не HCL | Обычный plan после refresh обнаруживает фактическое расхождение; вернуть через согласованный apply |
| Без refresh | На том же drift выполнить `plan -refresh=false` | Сравнить с обычным plan и объяснить, почему устаревший state может скрывать изменение |
| Lock | Удержать lock одной разрешённой операцией, второй дать короткий lock timeout | Второй процесс завершается ошибкой, не записывает state; после освобождения повтор проходит |
| Stale saved plan | Сохранить plan, другой операцией изменить state, попробовать первый plan | Apply отклоняет устаревший plan; новый план проходит review |

Коды `plan -detailed-exitcode`: 0 — нет изменений, 1 — ошибка, 2 — изменения. Сохранить код непосредственно, не потерять за `tee`, `|| true` или общей оболочкой. Эти значения не переносить автоматически на другие команды. [Семантика plan](https://developer.hashicorp.com/terraform/cli/commands/plan).

Подтверждение local lock не закрывает remote lock; `terraform_data` не доказывает реальные VM/IAM/drift provider. Перед cloud apply — квоты, датированный бюджет, scope и проверенный план. При частичном выполнении сверить state с инвентарём, сохранить созданное, пересчитать план. Отдельный негативный IAM-опыт проводится на disposable объекте; отсутствующее поле API проверяется полной проекцией.

## Ansible: тема 25

На чистой выбранной VM выполнить роли и записать PID, хеш управляемого несекретного конфига и HTTP. При неизменном втором запуске нужны `changed=0` **и** прежние PID/хеш, успешный HTTP. `changed_when: false` не является исправлением безусловного restart. Конфигурация меняется через template/copy, перезапуск — через соответствующий handler.

Изменить один proxy template: меняется только нужный конфиг и срабатывает только его handler. Затем повторить — изменений нет. Check-mode проверять отдельно: сравнить до/после файлы, PID и результат приложения; не считать флаг `--check` универсальным доказательством отсутствия побочных эффектов пользовательского shell. Секретные операции имеют `no_log: true` и `diff: false`; общий запуск с `--diff` не раскрывает их. Доказательства не содержат значений секретов.

Сверить поддержку check/diff выбранными модулями с [документацией Ansible](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_checkmode.html); неподдерживаемую проверку обозначить как ограничение и подтвердить отсутствие изменений наблюдением.

После ручной диагностики закрепить исправление в роли, повторить на чистом стенде и проверить неизменный повтор. Сохранить адрес/источник inventory и владельца VM, не переключаться случайно на рабочий хост.

## Совместимый релиз: темы 26 и 30

До изменения определить таблицу ожидаемой совместимости; не считать все сочетания автоматически допустимыми:

| API | Worker | Схема / событие | Ожидание и проверка |
| --- | --- | --- | --- |
| Старый | Старый | Расширенная / v1 | Чтение/запись и исходные операции после expand |
| Новый | Старый | Расширенная / совместимое событие | Новое поле необязательно, старый consumer не ломается |
| Старый после rollback | Новый или откатанный по плану | Расширенная / событие в очереди | Обработка накопленного и отсутствие повторного эффекта |
| Новый | Новый | Расширенная, backfill выполнен | Новый сценарий и повтор backfill без новых изменений |

Для несовместимого сочетания заранее определить запрет/порядок обновления и проверить блокировку. Contract-удаление старого поля не проводить до закрытия окна отката.

Практика темы 26: один immutable digest продвигается staging → production; после успешной сборки выполняется запуск настоящего образа. Намеренно неверный CMD может пройти unit-тесты, поэтому нужен runtime smoke. После выполненной expand-миграции выпустить неисправный образ, откатить к прежнему бинарнику и проверить старое чтение/запись, количество заказов/суммы, повтор backfill, сохранение схемы. Production остаётся заблокированным до исправления. Overlays, env allowlist и `needs` сверить с [правилами GitLab](gitlab-labs.md).

Тема 30 добавляет [долговечный платёжный эмулятор](business-contract.md): фиксация выплаты перед потерянным ответом, рестарт провайдера, повтор ключа, сверка pending и реальная смена API/worker-образов. Ожидается одна выплата по журналу провайдера, восстановимое состояние заказа и отсутствие повторного возврата в остаток. Простое переключение флага в одном процессе не подтверждает совместимость бинарников.

## Kubernetes и Helm: темы 27–28

До установки записать дату и фактические версии Kubernetes, runtime, kind/другого локального кластера, CNI, metrics-server, Helm и архитектуру образов; для каждой возможности — ссылку на документацию и результат runtime-проверки. Не закреплять универсальную «вечную» совместимость. Не устанавливать второй CNI, не проверив возможности текущего.

Инструменты, переданные в runner/DinD/node, проверять на месте исполнения: executable, SHA256 и `version`. Успех `docker cp` в одном контейнере не подтверждает наличие бинарника в другом. Делать эту проверку до долгого запуска зависимостей.

Различать локальную readiness процесса и маршрут клиента. Пример отказа: PostgreSQL получает `PGHOST=db` через общий env, а `pg_isready` без явного host обращается к собственному Service; неготовый Pod не попадает в endpoints, и готовность замыкается сама на себя. Для локальной проверки указать собственный адрес/сокет; затем отдельно проверить клиентский Service, EndpointSlice, DNS и миграции. Увеличение timeout не устраняет ошибку маршрута. Документация: [pg_isready](https://www.postgresql.org/docs/current/app-pg-isready.html), [probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/).

После Helm `--wait` выполнить бизнес-smoke через Service. В негативном опыте изменить selector: Pod Ready, но EndpointSlice без нужного backend и HTTP не проходит. Gate блокирует последующее окружение. После исправления повторяется тот же маршрут, а не только render/lint.

До cleanup собрать диагностику с общим deadline и ограничением объёма: Pod/PVC/Service/EndpointSlice, события, describe упавших workload, текущие и предыдущие логи **каждой** упавшей зависимости (включая брокер). Предыдущий лог может отсутствовать — отметить это. Не выгружать Secrets, kubeconfig, registry auth, значения env и сырые чувствительные describe/logs в открытые artifacts; сначала фильтровать. Если причина не установлена до удаления, так и написать, не приписывать её запланированному дефекту. Удалять только созданный данным запуском namespace/кластер; ошибка сбора не должна скрывать исходный failed exit.

| Свойство | Обязательная наблюдаемая проверка |
| --- | --- |
| NetworkPolicy | Из контрольного Pod разрешённый маршрут работает, запрещённый блокируется; labels и CNI известны |
| HPA | Метрики реально доступны, заданы requests, под нагрузкой меняется число реплик при достаточных ресурсах |
| PDB | Добровольное выселение через Eviction API соблюдает бюджет; обычное удаление Pod не является этим тестом |
| Graceful shutdown | В момент сигнала есть выполняющаяся задача; она завершается или безопасно повторяется по контракту без двойного эффекта |
| Readiness и Service | Локально Ready и реальный маршрут клиента работают; негативный selector закрывает gate |

Сопоставить ограничения PDB с [официальной документацией](https://kubernetes.io/docs/tasks/run-application/configure-pdb/). Рендер YAML подтверждает только конфигурацию, не эти результаты.

## Резервные копии и инциденты: тема 29

1. До опыта определить RPO/RTO, часы и способ измерения. Сохранить набор заказов, остатков, событий и контрольные суммы; сделать копию с идентификатором и подтверждённой точкой консистентности данных.
2. После этой точки записать отдельный узнаваемый заказ. Зафиксировать время учебной потери данных и начать таймер недоступности. Исходную БД не уничтожать до наличия проверяемой копии; потерю моделировать изоляцией отдельного экземпляра.
3. Восстановить в другую БД, сверить старые записи и определить судьбу post-backup заказа. RPO сравнивать с фактическим потерянным интервалом по сохранённым событиям/времени, а не по длительности команды backup. RTO останавливать, когда оговорённый пользовательский сценарий и требуемые проекции снова работают, а не при завершении `pg_restore`.
4. Перестроить поиск и аналитику из источника. Старые receipts/offsets не должны помешать наполнению новой проекции; новая генерация проекции получает своё пространство обработки. Сверить количество, деньги, удаления и повтор replay без дублей.
5. Проверить retention с корректными и повреждённой новой копией: плохая копия не вытесняет последние проверенные хорошие. Сохранять журнал проверки и установленное число/возраст пригодных копий. Провести восстановление ключа из отдельно управляемого источника; ключ рядом с единственным зашифрованным dump не решает задачу потери хоста.
6. Offsite проверяется при недоступном исходном хосте: другой хост/объектное хранилище и доступная процедура восстановления. Две папки одного диска не являются offsite. IAM negative DELETE проверять на отдельном disposable объекте, не на последней копии.
7. Таймлайн: сигнал → диагноз и гипотезы → действие → проверенное восстановление → влияние → конкретная правка. Сообщение о статусе подготовить как учебный артефакт; отправка другим людям требует отдельного поручения. Исправление закрепить в коде/конфигурации и повторить исходный отказ.
