# Банк диагностических заданий

Редакция: 2026-10-06. Карточки для преподавателя. Ученику сначала выдавать симптом, исходные материалы, границы и критерии; конкретное внесённое изменение и подсказку открывать после попытки. Намеренные дефекты существуют только в собственной изолированной копии лаборатории, никогда в реальном deployment.

Для всех 11 карточек подготовлен [запускаемый комплект](../assets/labs/README.md): prepare/check/reset, отдельные данные и evidence, эталоны для автора. Выбрать реальный backend по матрице комплекта; C12 имеет только локальную модель DAG, B29 — упражнение SQLite. Их успешный результат не закрывает hosted CI или PostgreSQL/offsite. Для каждого опыта отдельно фиксировать, что выполнено, что проверено только по структуре и какой runtime ещё недоступен.

## Подготовить один опыт

1. Взять работающую сдачу соответствующей темы, её commit/копию, lockfiles, fixture и паспорт. Один раз воспроизвести исходную проверку на чистой копии. Если она уже не проходит, исправить подготовку до внесения дефекта.
2. Создать отдельный каталог и namespace/Compose project/VM для опыта, записать перечень принадлежащих ему ресурсов. Сохранить baseline-файлы отдельно от рабочих; это не требует Git-тегов. Представленные ниже snippets адаптировать к реальным именам и версиям, не использовать как слепую замену всего deployment.
3. Внести ровно один выбранный дефект. Сохранить bad-файл, команду и ожидаемый отказ; если упала подготовка раньше нужного шага, опыт не состоялся. Проверка должна возвращать ненулевой exit при нарушении критерия и хранить безопасную диагностику.
4. Ученик диагностирует, исправляет и сдаёт объяснение причины, diff, failed/fixed evidence и проверку прежнего поведения. После ручного исправления изменить исходную конфигурацию; после темы 25 — соответствующую роль, если она управляет ресурсом.
5. Сброс: сначала сохранить логи, затем вернуть baseline только в рабочую копию и повторить её apply/recreate. Persistent volumes не удаляются по умолчанию. Для задания на пустую БД использовать новый отдельный volume/БД с явным владельцем. Повторный запуск и сброс должны приводить к одному объявленному состоянию. `git reset --hard`, общий prune и удаление всех namespaces не являются процедурой сброса.

## Начальные неисправные фрагменты

Это заготовки для отдельной копии стенда, не готовые решения. Преподаватель заполняет placeholders из паспорта и подтверждает отказ до выдачи.

L02a — отдельный unit после установки учебного сервера: `ExecStart=/opt/orderflow-lab/venv/bin/pythno -m http.server 18090 --bind 127.0.0.1`. Проверка `systemctl is-active orderflow-lab` возвращает неуспех. Имена пользователя/каталогов и доступный порт подготовить заранее; не менять SSH-службу для этого опыта.

D10 — overlay к заведомо работающему учебному web-сервису, который слушает 80. В рабочей копии заменить только mapping, не накапливать два порта из merge Compose:

```yaml
services:
  web:
    ports:
      - "127.0.0.1:18090:81"
```

Проверка после готовности контейнера: `curl --fail --silent --show-error --max-time 5 http://127.0.0.1:18090/`. До/после recreate сверить заранее созданный маркер в томе. Проверять итоговый Compose безопасным `config --quiet`.

C12 — целый маленький pipeline для отдельной учебной ветки; deployment заменён безвредным marker-job, без production credentials. Shell-команды требуют POSIX-среду runner; image при необходимости выбирается в паспорте:

```yaml
stages: [build, verify, marker]
build:
  stage: build
  script: ["true"]
gate:
  stage: verify
  script: ["sleep 5", "exit 1"]
marker:
  stage: marker
  needs: [build]
  script: ["printf 'marker-ran\n'"]
```

Ученику требуется запретить marker при failed gate, затем проверить успешный gate. Для воспроизведения обхода нужны свободные executor slots и фактический запуск marker до завершения gate; задержка 5 секунд не гарантирует это при очереди runner. Если окно не воспроизведено, зафиксировать ограничение расписания и повторить в подходящей учебной среде, не объявлять неверный DAG исправным. Сохранить реальные job statuses/timestamps; CI lint одной структуры недостаточно. Сон здесь создаёт окно воспроизведения в учебном job, не способ синхронизации production.

T24 — использовать `terraform_data` из [упражнения state](gitlab-labs.md) в отдельном каталоге с локальным backend, изменить `input`. Неправильный проверяющий скрипт:

```sh
terraform plan -input=false -no-color
plan_status=$?
test "$plan_status" -eq 0
```

Он смешивает «нет изменений» с успешным plan изменений. Ученику нужен проверяющий с тремя различимыми исходами; отдельно проверить конфигурационную ошибку и неизменную конфигурацию. Файлы плана/state не публиковать.

A25 — после выдачи работающей роли добавить безусловную задачу (имя unit из паспорта):

```yaml
- name: Restart application
  ansible.builtin.systemd_service:
    name: orderflow-lab
    state: restarted
```

Проверка сопоставляет changed/PID/хеш, а не только stdout. Для сброса вернуть роль и выполнить её, не прятать изменение `changed_when: false`.

H28 — в копии исправного Service с label `app: orderflow-lab` у Pod задать:

```yaml
spec:
  selector:
    app: orderflow-lab-mismatch
```

Проверка: получить EndpointSlice по label `kubernetes.io/service-name=<имя>` и выполнить HTTP из контрольного клиента. Очистку выполнять после диагностики; не закрывать замечание одним исправленным YAML.

Для карточек R26/K27/B29 использовать существующий код соответствующей темы: самостоятельные приложения специально для этих поломок не нужны. Дополнительные случаи browser/OIDC, disk и IAM описаны в [среде](environment-guide.md) и [эксплуатационных практиках](operations-labs.md). Не воспроизводить ENOSPC заполнением основного диска и не удалять единственный backup для имитации отказа.
