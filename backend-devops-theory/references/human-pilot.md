# Пилот с реальным участником

Статус комплекта: подготовлен. Проведённым пилотом считается только сессия с реальным участником и его собственными ответами/кодом. Автор, агент и синтетический диалог не могут быть записаны как такой участник. Не выводить эффективность курса из одной успешной технической проверки.

## Подготовка ведущего

Первый участник — разработчик или QA Automation с основами Python и SQL; опыт и знакомство с транзакциями записать кратко, без персональных данных. Пилот — 45–60 минут по 08/2, затем короткая отсроченная проверка при согласии участника. Это проверка конкретного урока и ревью, не сокращённый двухчасовой курс и не входной языковой блок.

До встречи ведущий готовит [PostgreSQL-стенд](../assets/backend-labs/README.md), отдельный B08R и проверяет его готовность. Участнику выдаются условие и неисправный `submission.py`; GOOD/reference и авторский audit не показываются. Все данные синтетические. Сохранение учебных ответов/кода согласуется с участником; аудио/видео не нужны. Вести отдельный каталог пилота, не состояние существующего ученика.

## Сессия

1. **5 минут, исходное понимание.** Без подсказки: «Что гарантирует atomic?» и «Доказывает ли stock=0, что последний товар куплен только один раз?». Сохранить точный ответ, не исправлять его до фиксации.
2. **10–15 минут, урок.** Выдать объяснение 08/2 по скиллу. Отметить вопросы и места, где понадобилось пояснение. Участник должен своими словами построить расписание двух запросов, а не повторить определение.
3. **15–20 минут, самостоятельная практика.** Исправить B08R, предъявить diff и evidence. Записать время до первой попытки, число запусков и запросов подсказки. Подсказки выдавать ступенчато: область критического действия → механизм БД → конкретный пример только по просьбе. Сбой стенда записывать отдельно от ошибки ученика; технический перерыв не считать временем решения.
4. **10 минут, ревью и перенос.** Замечание содержит критерий, строку, механизм и следующий шаг. После исправления попросить объяснить новый случай: stock=3, два запроса по quantity=2. Ожидается один заказ и остаток 1; участник объясняет, какое расписание и состояние БД нужно проверить. Это отдельный мысленный перенос, не выполненный runtime-тест.
5. **5 минут, обратная связь.** Что было непонятно в условии, какое замечание помогло, где ведущий выдал слишком много/мало? Просить конкретную фразу/шаг, а не только оценку «понравилось».

По согласованному последующему обращению через 24–48 часов дать похожий вопрос без исходного ответа. Не назначать автоматическое напоминание без просьбы. Отсутствие повторной встречи не подменять результатом «запомнил».

## Форма наблюдений

| Поле | Запись |
| --- | --- |
| Участник | Анонимный ID; опыт Python/SQL/QA |
| Материалы | Snapshot SHA256, версия задания, дата, доступный инструмент/модель преподавателя |
| До урока | Два дословных ответа и неопределённости |
| Самостоятельная попытка | Diff, команды, выходы, evidence и затраченное время |
| Подсказки | Точный запрос/ответ и момент; отделить просьбу решения от просьбы направления |
| Ревью | Какие замечания приняты/оспорены; проверены ли исправления |
| Перенос | Ответ stock=3/qty=2, объяснение конкуренции и плана проверки |
| Среда | Инциденты и длительность отдельно от учебных ошибок |
| После паузы | Выполнено/не выполнено; собственный ответ без подсказки |
| Изменение курса | Наблюдение → причина → конкретная правка → критерий следующего пилота |

Критерии пилота заранее: участник различает атомарность и защиту от гонки; самостоятельно объясняет корректный исход и метод проверки; после понятного ревью устраняет дефект без скрытого изменения контракта. Зелёный check при неспособности объяснить решение отмечается как технический успех с непроверенным пониманием. Одной сессии достаточно для списка затруднений, но недостаточно для вывода о типичном времени обучения или проценте успеха аудитории. Следующий разумный шаг — повторить изменённый урок с другим участником соответствующего профиля.
