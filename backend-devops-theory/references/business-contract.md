# Пример версионируемого контракта OrderFlow

Учебный пример v1, 2026-10-06. Преподаватель и ученик выбирают конкретные правила до кода; пример не переопределяет уже принятое задание. В теме 03 вводятся HTTP-правила, в 04 — схема, в 06–08 — реализация и конкуренция, в 30 — возврат. Будущие разделы не становятся ранними требованиями.

## Заказ: темы 03–08

- Деньги: целое число минимальных денежных единиц одной явно выбранной валюты; boolean, дроби, отрицательные суммы не принимаются. Альтернатива — Decimal/NUMERIC с заранее объявленной шкалой. Цена приходит из каталога, в позиции сохраняется snapshot; изменение каталога не меняет заказ. Единицу API и SQL не смешивать.
- Количество — положительное целое, не boolean. Итог = сумма `unit_price_snapshot * quantity` на сервере. Для неизменного ключа сортировка полей JSON не должна случайно менять смысл тела: выбрать и описать каноническое представление, включая порядок позиций и отсутствие/наличие необязательных полей.
- Переходы v1: `new → confirmed → shipped → completed`; отмена из `new` и `confirmed`, остаток возвращается один раз; повтор отмены возвращает сохранённый результат без приращения. Переход из `shipped` в отмену даёт конфликт. История хранит инициатора и время.
- Пример области ключа: `(buyer_id, operation, Idempotency-Key)`. Ключ регистрозависим, пробелы на краях запрещены. Один ключ и канонически одинаковое тело → исходный статус/тело; иное тело → 409. Срок хранения результата и поведение после истечения задать явно, не «забывать» ключ во время эксперимента.

| Действие | buyer | operator | admin |
| --- | --- | --- | --- |
| Читать заказ | Свой | Любой | Любой |
| Создать / отменить | Свой, по переходам | Отмена по переходам | По тем же переходам |
| confirmed/shipped/completed | Нет | По переходам | По переходам |
| Менять каталог и остатки | Нет | Нет в v1 | Через контролируемую операцию |
| Выдавать роль | Нет | Нет | Отдельный административный путь |

Выбранные 403/404 для чужого объекта зафиксировать в HTTP-контракте. Поле `user_id` из тела не даёт прав. Admin не обходит инварианты: в теме 08 проверить старую форму, открытую до резервирования, и повтор POST формы; абсолютная запись старого остатка не должна возвращать проданный товар.

## Малый контрольный SQL-набор

В теме 04 возвраты — предоставленные табличные данные для агрегирования, без реализации процесса темы 30. Идентификаторы и суммы синтетические; валюта одна, суммы в минимальных единицах.

```sql
WITH items(order_id, item_id, qty, unit_price) AS (
  VALUES (1, 11, 2, 100), (1, 12, 1, 300), (2, 21, 1, 200)
), refunds(item_id, amount) AS (
  VALUES (11, 100), (11, 100), (12, 100)
)
SELECT * FROM items ORDER BY order_id, item_id;
```

Дать ученику эти данные и задание отдельно вычислить валовую сумму, возврат и чистую сумму по заказу. Эталон: заказ 1 — 500, 300, 200; заказ 2 — 200, 0, 200; всего — 700, 300, 400. У позиции 11 две строки возврата: прямой JOIN до суммы позиций выявляет двойной счёт. Решение агрегирующего запроса ученик пишет сам. При сравнении ORM/N+1 в теме 08 использовать одинаковый `ORDER BY` по уникальному ключу и одинаковый fixture.

## Возврат: тема 30

Новая версия контракта определяет допустимые статусы, количество ещё не возвращённых единиц, сумму, возврат в остаток и права. Возврат части позиции не должен превышать её snapshot-сумму за вычетом уже возвращённого; правила округления и частичной компенсации объявляются до реализации.

Платёжный эмулятор — отдельный процесс со своим долговечным хранилищем операций, ключом идемпотентности и запросом результата. Его рестарт не стирает выполненную выплату. Сценарии: нормальный ответ, отказ до эффекта, потеря ответа после commit провайдера, повтор, рестарт провайдера, сверка неизвестного исхода. Не превращать `timeout` в «успех» или безусловную новую выплату. До сверки хранить восстановимое pending-состояние.

Для выпуска и отката сопоставить старый/новый API, worker, версию события, схему БД и контракт эмулятора. В теме 26 упражнение выполняется на уже существующем изменении заказа/доставки; денежная операция добавляется только в теме 30. Проверять реальную смену образа, чтение/запись старым кодом после expand-миграции, повтор backfill и незавершённую операцию после отката. Таблица совместимости и доказательства входят в [эксплуатационные практики](operations-labs.md).
