# Контрпримеры для тем 13–19

Редакция 2026-10-12 по F19–F31. Читать раздел текущей части; объявлять выбранные проверки до выполнения задания. Историческое наблюдение — основание примера, а не обещание одинакового поведения всех версий библиотек.

## 13/2–3: подстановка и внешний владелец (F19, F20)

Typecheck определения LocalDelivery с quote→str может быть зелёным, пока класс нигде не подставлен вместо Delivery с quote→Quote. Включить в область проверки точку композиции `adapter: Delivery = LocalDelivery()` либо типизированного потребителя. После исправления проверить те же файлы и runtime-валидацию внешнего ответа: Protocol её не выполняет.

Открытое соединение после generator export ещё не доказывает сохранение чужой транзакции. Владелец создаёт незакоммиченный marker; при full/break/исключении потребителя проверить INTRANS до нового SQL, невидимость marker независимому observer и успешный rollback владельца. Exporter закрывает собственный cursor, но не commit/rollback/close переданного соединения. Проверка собственного соединения — отдельный положительный случай.

## 14/2–3: общий deadline и два ограничителя (F21, F22)

Общий бюджет включает ожидание semaphore/pool, запросы и retry delay. Равные внутренний HTTPX timeout и внешний asyncio timeout могут конкурировать; конкретный аудит воспроизвёл ReadTimeout при уже запрошенной отмене и лишний retry. Это наблюдение определённой матрицы, не универсальный дефект HTTPX.

В управляемом опыте задержать event loop около expiry и сохранить тип ошибки, task.cancelling(), число попыток и полное elapsed. Сравнить с одним владельцем общего deadline: внутри ограниченной области HTTPX `timeout=None`; снаружи этой области отключать timeout нельзя. Внешнюю отмену распространять после cleanup, при запрошенной отмене не начинать новую попытку. HTTPX различает connect/read/write/pool timeout; каждый из них не является общим сроком бизнес-операции. [HTTPX timeouts](https://www.python-httpx.org/advanced/timeouts/), [asyncio timeout](https://docs.python.org/3.12/library/asyncio-task.html#timeouts).

Проверить semaphore2/pool20, затем semaphore3/pool1: одинаковые лимиты могут маскировать отсутствие одного механизма. Два одновременных вызова collect отдельно выявляют область semaphore: локальный лимит 2 каждого допускает aggregate4. Измерять фактические активные обращения и очередь, не значение настройки. Объявить, принадлежит ли лимит запросу, процессу или всему приложению.

## 15/3: отсутствующее поле, null и shutdown (F23, F24)

В Pydantic2 `instructions: str | None = Field(max_length=240)` допускает null, но не отсутствие. Для необязательного поля нужен явный default. Проверить три запроса: без поля, null, строка; затем неверный тип/длина и повтор с изменением именно нового поля →409. Старый неизменённый клиент должен работать с новым сервером. Обратное направление не подразумевается: old server с extra=forbid может отвергать новое поле. [Pydantic fields](https://docs.pydantic.dev/latest/concepts/fields/).

В Compose команда `alembic ... && exec uvicorn ...` передаёт сигнал серверу после миграции; без exec оболочка может удержать его. В опыте проверять событие ASGI shutdown, закрытие клиента и dispose engine, отсутствие оставшихся процессов. Один ExitCode143 не различает достигнутый и пропущенный lifespan: поведение exit code зависит от сервера/версии. Сравнить журнал startup→shutdown при одинаковом способе остановки.

## 16/1–3: владелец lease, испорченная копия и hit ratio (F25–F27)

Два независимых требования для lease: прежний владелец не удаляет блокировку преемника **и** не публикует поверх его свежего кеша. Compare-delete защищает только первое. Управляемо задержать A, дождаться истечения lease, подтвердить успешный SET NX нового token B и публикацию B, затем отпустить A. Сохранить token и значение B. Сравнение token и запись кеша должны быть атомарными, например в одном Lua helper:

```lua
-- KEYS: lock, cache; ARGV: owner token, JSON value, TTL seconds
if redis.call('GET', KEYS[1]) == ARGV[1] then
    redis.call('SET', KEYS[2], ARGV[2], 'EX', ARGV[3])
    return 1
end
return 0
```

Разобрать helper до самостоятельной работы. При Redis Cluster оба ключа должны быть доступны одной script execution, обычно через общий hash tag. Это защита публикации кеша, не fencing основной бизнес-транзакции и не строгая согласованность всей системы. [Атомарность Redis scripts](https://redis.io/docs/latest/develop/programmability/eval-intro/).

При повреждённом JSON кеш трактуется как miss: при доступной PG — SELECT, ответ 200 и исправленная копия. Удаляя плохое значение, атомарно сравнить его с прочитанной версией, чтобы не стереть конкурентную замену. Ошибку PG не превращать в пустой успех. Проверка одного повреждённого JSON не подтверждает валидацию всех семантически неверных объектов.

Показать два разных товара и общий неверный ключ: hit ratio может быть 96,7% при неправильной цене. Сверять actor/product scope, ответ с независимым источником и SQL cold/hit/expiry. Более низкий hit ratio при верных данных может быть правильным результатом.

## 17: отправленный ack и срок публикации (F28, F29)

Настройка early ack ещё не означает, что AMQP basic_ack ушёл до SIGKILL. Зафиксировать pool и точку наблюдения. В отрицательном контроле удержать prefork child до эффекта, наблюдать отправку ack главным процессом, затем остановить только собственную группу. Сопоставить ready/unacked, факт redelivery и эффект в БД. Если ack не наблюдался, потеря сообщения этим опытом не доказана. Late ack также требует проверки выбранной политики worker loss; [Celery acknowledgements](https://docs.celeryq.dev/en/stable/userguide/tasks.html#acks-late).

Connect timeout не ограничивает DNS, retry/reconnect и весь dispatcher attempt. Проверить отдельно потерю broker DNS и отказ доступного адреса. Объявить общий прикладной бюджет или внешний watchdog; если только watchdog завершил publisher, писать «ограничен проверяющим», не «приложение уложилось в срок». После остановки intent остаётся pending; после восстановления оно доставляется, повтор не удваивает эффект. Время DNS и транспорта сохранять отдельно.

## 18/2: медленный отправитель (F30)

Удержать sender, выполнить несколько настоящих обновлений PG, измерить реальную очередь извне и затем отпустить отправку. Если договор — последний snapshot, клиент получает последнее состояние, очередь ограничена. Внутренний queue_peak==1 сам по себе не доказательство: счётчик мог не обновляться. Явно назвать удерживаемый sender моделью медленной отправки, не TCP stress test.

## 19/2–3: отрицательные JWT доходят до нужного claim (F31)

Для audience/nonce/expiry использовать token, правильно подписанный доверенным тестовым ключом; менять ровно проверяемое поле, остальные сохранять корректными. Иначе отказ подписи скрывает отсутствие claim-проверки. Для scope сравнивать точный элемент: delivery:create-extra не даёт delivery:create.

Отдельно проверить неверную подпись/alg, unknown kid, отсутствие обязательного exp и допустимый token. PKCE, одноразовость code и ротацию подтверждать настоящим учебным provider, не только mock обменом. В отчёте сохранять статусы/причины, не credential. Матрица целевых отказов объявляется до реализации.
